# E2 campaigns

How E2 is run, for a reader who measures a campaign or adds an arm. An E2 point is one arm file in [`arms/`](arms): the calls, the agent replay beside them, the gateway's configuration and the engine ([the arm-file reference](../../python/flatshare_bench/README.md#e2-points)). `flatshare-bench e2 run` measures one point on cyan. A campaign file lists arm files, and `campaign.sh` measures them in order from a workstation with SSH to the hosts, the way `deploy/deploy.sh` deploys. A line `agents-seed N` in it sets AIPerf's seed for all of its points, in place of each arm file's `[agents] seed`, so that each round of a repeated campaign replays a workload sample of its own while its points stay paired. A line `kv-sample-s SECONDS` sets `flatshare-bench e2 run --kv-sample-s` for its points: how often an agent point samples the engine's KV use and requests for the measured running share (0.5 s by default, on one connection to the engine that it keeps for the calls); `kv-sample-s 0` samples nothing, as W5's points ran, the sampler having come after them, so that a campaign read against W5's matches its instrumentation (the Marlin dry run's point, `benchmarks/a100/marlin-dry.campaign`). A line `save-audio` has the callers save each call's audio, for [the demo video](#the-demo-video) (`flatshare-bench e2 run --save-audio`).

```sh
export FLATSHARE_SSH="ssh -F $HOME/.ssh/flatshare_config"             # your SSH command for the hosts, as for deploy.sh
benchmarks/e2/campaign.sh --dry-run benchmarks/e2/w2.campaign   # check every arm file; list the points and engines
benchmarks/e2/campaign.sh --pause benchmarks/e2/w2.campaign     # measure, then pause the GPU node
```

For each point whose run directory on cyan is not complete, `campaign.sh`:

1. switches the GPU node to the arm's engine with [`variant.sh use`](../../deploy/phastform/variants/README.md), which restarts only what changes and returns once the engine answers `/health`;
2. runs `flatshare-bench e2 run` on cyan, into `~/flatshare/runs/e2/CAMPAIGN/POINT`, with the GPU node's deployed revision, its `~/flatshare/src/DEPLOYED` read over SSH as the point starts, which `run.json` keeps beside cyan's (`--gpu-source`). Meanwhile it samples the GPU node's `nvidia-smi` once a second (SM and memory clocks, temperature, power and clock event reasons, timestamps in UTC, and the GPU's name, so that a record says which card it ran on), because a consumer card's boost clock follows its temperature, and puts the samples into that directory as `gpu.csv` when the point ends, failed or not;
3. fetches that directory into `$FLATSHARE_E2_RESULTS/CAMPAIGN/POINT` (default `~/flatshare/runs/e2`), without AIPerf's `inputs.json`.

A complete point is skipped, so running a stopped campaign again resumes it. The first failure stops the campaign, with the partial run directory fetched and its `run.json` saying what failed. At the end, `flatshare-bench e2 report` writes the frontier of the campaign's points (fetched into `CAMPAIGN/report`: `frontier.md`, `frontier.csv` and a figure per workload, `frontier.svg` for the arm files' own) and `flatshare-bench e2 reset` puts cyan's units back. `--pause` then stops the GPU node's units, which nothing should hold while idle. A campaign that fails once it has switched the node does both on its way out too, unless a point may still be running on cyan, which a reset or a pause would spoil: its lock is held, or the connection to cyan was lost (ssh's exit status 255, which `campaign.sh` reports as such rather than as the answer of the probe it cut). It then leaves cyan's units and the node as they are, and says so. `campaign.log` beside the points keeps every step.

Points that share an engine go together in a campaign file: a switch restarts the engine, about 2 minutes with warm caches. A point takes about 12 minutes: AIPerf builds its dataset for about 4, then a minute of warm-up and the calls. AIPerf's cache keeps that dataset for the campaign's later points that replay the same corpus with the same seed, and they load it instead (`configs/aiperf.env`): on peacock, over the 48 long traces, AIPerf's profiling phase began 143 s after its start when it built their dataset and 9 s after when it loaded it, where each of the A100 run's points built it for 135 s.

**On Gray.** `FLATSHARE_GPU` names the campaign's one GPU node, Phastform by default. With `FLATSHARE_GPU=gray` the campaign switches Gray's engine, samples Gray's GPU and passes `--node gray` with Gray's revision to every point: each one reads Gray's engine through `flatshare-tunnel@gray` on cyan (started when it is not running), with cyan's gateway and voice worker pointed at Gray's sockets for the campaign's points (`gray-engine.sock`, `gray-stt.sock`, `gray-tts.sock`) and put back by the reset at its end, and every record names the node it ran on beside the node's deployed revision ([the GPU node](../../python/flatshare_bench/README.md#e2-points)). A campaign's run directories on cyan hold one node's points: run on Gray, a campaign whose directory already holds a point measured on Phastform stops at that point rather than fetch it as Gray's, so each node's rounds are campaign files of their own (`rg-r1-gray.campaign` beside `rg-r1-phastform.campaign`, say). Gray needs, once: its release (`deploy/deploy.sh gray`; it runs its servers in the host's network namespace, its kernel refusing unprivileged user namespaces, [the runbook](../../ops/RUNBOOK.md#a-gpu-node-without-user-namespaces-gray)), its models (`bash ~/flatshare/src/deploy/gray/bootstrap.sh`), cyan's tunnel keys on it (`deploy/authorize-tunnel.sh cyan gray`), and on cyan `~/.config/flatshare/tunnel-gray.env` with `FLATSHARE_TUNNEL_TARGET=<user>@<gray's host>`.

[`gray-smoke.campaign`](gray-smoke.campaign) checks Gray end to end on W5's round-1 sample of the agents: voice alone on the frozen box, then the agents alone on a dedicated card ([`rg-disc-agents-only-s24`](arms/rg-disc-agents-only-s24.toml), which stops the card's speech servers) and on the shared card's engine ([`rg-disc-agents-pr-ab48-s24`](arms/rg-disc-agents-pr-ab48-s24.toml), W5's configuration of the PRs, which starts them again):

```sh
FLATSHARE_GPU=gray benchmarks/e2/campaign.sh --dry-run benchmarks/e2/gray-smoke.campaign   # the points and engines
FLATSHARE_GPU=gray benchmarks/e2/campaign.sh --pause benchmarks/e2/gray-smoke.campaign     # measure on Gray, then pause it
```

**Points without calls.** An arm file with `[voice] callers = 0` and agent sessions measures the agents alone, as a card that serves no call runs them: no callers and no worker journal, its window `[agents] window_s` after the warm-up (355 s by default, the median length of a two-caller point's calls in W5's records), its goodput the point's measure. With `[engine] variant = "agents-only"` the card runs without its speech servers, the engine's KV pool grown into their memory under vLLM's own scheduling for the card ([the variant](../../deploy/phastform/variants/README.md#a-card-for-the-agents-alone)): the resource gate's best practical dedicated card. Its controlled counterpart is the same point on the shared card's engine, the speech servers resident and idle. The report gives such points a workload of their own, without a frontier or a figure.

**On one host.** `campaign.sh --local` runs a campaign on a single host that is cyan and the GPU node at once ([docs/HARDWARE.md](../../docs/HARDWARE.md#single-host-mode)): every step runs there (`deploy/bin/flatshare-local` in place of ssh, so a dropped workstation link does not stop it), the node is `localhost`, its engine switches through `$FLATSHARE_NODE_DIR/variant.sh` (a node rendered from a hardware profile has its own, `FLATSHARE_NODE_DIR=flatshare/node`), and the results go to `~/flatshare/results/e2`, which `deploy/a100/pull.sh HOST` copies to the workstation every two minutes.

**A deadline.** `--until HH:MM` (UTC; tomorrow's once today's has passed) starts no point that would end after then; the frontier and the reset follow as usual. A point is budgeted by the longest of its kind, and of an engine switch, measured on this host (`durations.tsv` beside the campaigns' results), and until one is, by W5's durations: 13 minutes for a point with agents, 7 without, and 2 more for an engine switch. `--until-epoch SECONDS` sets the deadline as an absolute time, which has no tomorrow: `benchmarks/a100/run.sh` hands its one deadline as an epoch to every campaign of a run and to `cprime.sh`, so that a campaign that starts after HH:MM is not given a deadline a day away. A campaign stopped by its deadline exits 0 as a complete one does, and the two scripts tell them apart by the campaign's points, which `campaign.sh --points CAMPAIGN` prints, one a line, as it reads the file, without reaching a host.

**Stopping.** Ctrl-C stops `campaign.sh` and its sampling of the GPU, but a point already running on cyan goes on to its end: closing its SSH session does not stop it. To stop it as well, send SIGINT to its pid, which `~/flatshare/runs/.flatshare-bench-e2.lock` holds on cyan; `flatshare-bench e2 run` then stops AIPerf and the callers and marks the point failed. While a point runs, `campaign.sh` refuses to switch the engine under it.

## Before the first campaign

- Deploy both hosts (`deploy/deploy.sh`): each release builds or links the host's environments from their locks, cyan's `venvs/bench` and `venvs/smg` among them ([the runbook](../../ops/RUNBOOK.md#deploy)).
- cyan: the `vad-turns` worker variant is linked and the worker runs bench mode, not the `serve` variant (`flatshare-bench e2 run` refuses to measure otherwise); `~/.config/flatshare/gateway-keys.env` has `FLATSHARE_GATEWAY_AGENTS_KEY`, the key of the `agents` tenant; `~/flatshare/data/weka-x32` (`flatshare-bench scale-traces`) and `~/flatshare/data/callers` (`flatshare-voice render-callers`) exist; `flatshare-gateway` is a build that knows every key the arms' `[gateway]` tables set (`upstream_priority`, `[admission]`).
- Phastform, for arm 7b: `bash ~/flatshare/src/deploy/phastform/variants/sglang/install.sh` builds SGLang's environment once.

[`w2b.campaign`](w2b.campaign) holds W2's second batch, written from the first batch's results. At 16 sessions the best arm 4 cells, step cap 1024 with no long-prefill threshold and the frozen box (512/256), were within noise of each other (V2V p95 2,167 and 2,215 ms over 50 turns, background goodput within 4%), so both are measured again at 24 sessions, and the frozen box, the configuration every earlier result was measured on, is the engine of the other points: arm 5 (`--watermark 0.1`; `--max-num-queued-tokens 8192`, about 1.6 s of prefill at the step cap), arm 6 (caps of 2 and 8; a reservation of 2,048 tokens, two concurrent voice turns at their longest), arms 8a–8c (flow-control ceilings 6/6/6, so that background fills at most 6 and a realtime request sheds), preemptive generation off, and 4 and 6 callers. The admission arms wait at most 240 s, below the replay's 300 s request timeout.

**The discriminating scenario** replays only the traces with the largest contexts, so that agents fill the KV pool while voice turns keep arriving. `weka-x32-long` on cyan holds the 48 traces of `weka-x32` whose main agent has the largest median input (the median trace's median is 13,326 tokens against 4,784 for the whole corpus; per request, 13,927 tokens against 7,940; 23,848 main-agent requests), linked by [`long_traces.py`](long_traces.py): `python benchmarks/e2/long_traces.py ~/flatshare/data/weka-x32 ~/flatshare/data/weka-x32-long 48`. Its points are named `disc-*`.

[`w2c.campaign`](w2c.campaign) holds W2's third batch: arms 4 to 8 in the discriminating scenario, one run each (the arm files `disc-<arm>-s24.toml` are the 16- or 24-session arms with `sessions = 24` and `data = "weka-x32-long"`), and SGLang with its host tier (`--enable-hierarchical-cache --hicache-ratio 4 --hicache-write-policy write_through`) at 8 and 16 sessions, for parity with vLLM's write-through CPU tier. W4 repeats the best of each arm beside arm 9. [`a9.campaign`](a9.campaign) holds arm 9 in the same scenario: the gateway's lifecycle policy (`[gateway.admission]` with `policy = "lifecycle"`: 1,024 tokens of KV headroom per armed session, a 150 ms critical-window budget of predicted background prefill, a 16-token reply cap when the headroom was not kept), the engine's `make-room` variant and the voice worker's lifecycle events; its knob, the critical-window budget at 0 and 500 ms; and one run of each single-mechanism ablation (`disc-a9-no-*`, `trigger-request`, `gateway-only`, `engine-only`). A switched-off mechanism's keys are left out: the gateway refuses them.

[`r1.campaign`](r1.campaign) to [`r4.campaign`](r4.campaign) repeat the discriminating scenario in rounds, so that each headline configuration has five runs (w2c and a9 are round 0) and each of arm 9's ablations three (rounds 1 and 2). The headline configurations are the best of each arm in round 0: the frozen box and the best step-cap cell (`disc-a4-b1024-t0-s24`), the static reservation, preempt-resubmit, SGLang with its host tier, and arm 9. A round groups its points by engine, and the groups' order rotates from round to round, so that no configuration always runs at the same hour of a campaign that takes hours. Rounds 3 and 4 and both standard rounds (below) also measure voice alone (`a1-voice`), the reference every point's SLO is read against, which W2 measured once: arm 9's runs land just above that SLO, by about the spread of one point's p95, with degrade capping every reply, so the reference itself needs repeats.

[`a9-standard.campaign`](a9-standard.campaign) puts arm 9 in the standard scenario at 8, 16 and 24 agent sessions, as W2 measured arms 2 to 8, so that its frontier stands beside theirs. [`s1.campaign`](s1.campaign) and [`s2.campaign`](s2.campaign) repeat the realistic operating point, 16 agent sessions, for the frozen box and arm 9, so that each has three runs there.

[`a9-window.campaign`](a9-window.campaign) measures arm 9 without degrade and with make-room's first-tokens window at 48 tokens, after `s2`: without degrade, a reply's first sentence can outrun the default 16-token window, and degrade's 16-token cap, which keeps it inside, capped every reply in the discriminating scenario.

[`upstream.campaign`](upstream.campaign) measures the engine as the PRs propose it, without the reserve and behind the gateway without an admission policy: the KV preemption alone, with the budget cap, and with a 48-token window. [`upstream-r1.campaign`](upstream-r1.campaign) and [`upstream-r2.campaign`](upstream-r2.campaign) repeat these three and arm 9's 48-token window, so that each has three runs, as each of arm 9's ablations has: a configuration that misses the SLO moved by up to 1.9 s in p95 from round to round.

[`w5-r1.campaign`](w5-r1.campaign) to [`w5-r5.campaign`](w5-r5.campaign) re-measure, after W5's fixes to make-room, the PRs' configuration with a 48-token window (`arms/w5-disc-pr-ab48-s24.toml`) beside its control, the same on make-room as v0.3 built it (`w5-disc-pr-ab48-v03-s24.toml`, on the `make-room-v03` variant: v0.3's `build.py` and `flatshare-engine.conf`, its module renamed), and beside voice alone and the frozen box (`w5-a1-voice.toml`, `w5-disc-frozen-s24.toml`) in the same rounds. Each arm file is its W4 one with each call opening with an unmeasured warm-up turn (`[voice] warmup_turns = 1`). Each round replays a sample of the agents of its own (`agents-seed` 11 to 15) and runs the four in an order rotated by one from round to round, so that each runs in each place. The control's module is `flatshare_make_room_v03_scheduler`, so that `flatshare-bench e2 run`'s engine check, which reads the engine's scheduler class back, fails a point on the other module before it starts.

[`w5-pr-r1.campaign`](w5-pr-r1.campaign) to [`w5-pr-r5.campaign`](w5-pr-r5.campaign) re-measure the PRs' configurations in rounds of their own: the KV preemption alone (`arms/w5-disc-pr-a-s24.toml`) and both PRs at the budget cap's default 16-token window (`w5-disc-pr-ab-s24.toml`), beside the frozen box and the 48-token window of W5's campaign, so that every configuration the PRs cite has its runs in the same rounds. Round N replays w5-rN's sample of the agents and runs the four in an order rotated by one from round to round; the frozen box and the 48-token window, measured in both campaigns, show how far the two sessions differ.

[`w5-ext-r1.campaign`](w5-ext-r1.campaign) to [`w5-ext-r5.campaign`](w5-ext-r5.campaign) extend W5's re-measure over the same five samples of the agents: preempt-resubmit, the best arm without an engine change, beside the PRs' 48-token configuration in the discriminating scenario (`arms/w5-disc-a8c-resubmit-s24.toml`, `w5-disc-pr-ab48-s24.toml`), and the frozen box and the PRs' 48-token configuration in the standard scenario, 16 agent sessions of the whole corpus (`w5-std-frozen-s16.toml`, `w5-std-pr-ab48-s16.toml`), each call opening with a warm-up turn. Each round runs three engine groups in an order rotated by one group from round to round; the PRs' two points share their engine.

[`w5-cap-r1.campaign`](w5-cap-r1.campaign) to [`w5-cap-r3.campaign`](w5-cap-r3.campaign) measure calls per GPU: the PRs' 48-token configuration with 4 and with 6 callers beside the discriminating scenario (`arms/w5-disc-pr-ab48-c4-s24.toml`, `w5-disc-pr-ab48-c6-s24.toml`), and voice alone with as many callers, the SLO's references (`w5-a1-voice-c4.toml`, `w5-a1-voice-c6.toml`), over three of W5's samples of the agents. Each round swaps the order of its two engine groups, and of the caller counts within each.

[`fb-r1.campaign`](fb-r1.campaign) to [`fb-r5.campaign`](fb-r5.campaign) are FB's rounds: voice alone, the frozen box and the PRs' 48-token configuration again, on the final code, with W5's arm files, W5's five samples of the agents (seeds 11 to 15) and no KV sampler, as W5's points ran, so that each round compares with W5's of the same seed. Each round rotates the three by one place. Their records are in [`benchmarks/results/2026-10-25-e2-fb`](../results/2026-10-25-e2-fb/README.md), whose `compare.py` sets each round beside W5's.

[`rs-r1.campaign`](rs-r1.campaign) to [`rs-r5.campaign`](rs-r5.campaign) are RS's rounds: the frozen box and the PRs' 48-token configuration on v1.2, with W5's arm files, W5's five samples of the agents (seeds 11 to 15) and the KV sampler every 0.5 s, so that the box's running share is measured as the A100 run measured its own. Odd rounds run the frozen box first, even rounds the PRs' configuration. Their records are in [`benchmarks/results/2026-10-26-e2-rs`](../results/2026-10-26-e2-rs/README.md), whose `running_share.py` sets each round beside the A100 core's of the same seed.

The `[admission]` keys are those of `flatshare-gateway`'s configuration ([its README](../../crates/flatshare-gateway/README.md)); `flatshare-bench e2 run` passes the `[gateway]` table through as it is.

`FLATSHARE_PROFILE` names the GPU node's hardware profile ([`deploy/profiles`](../../deploy/profiles)) when it is not the frozen box's: `flatshare-bench e2 run --profile` then holds the engine to that profile's model and scheduler settings, and the report gives the points a workload of their own, by the GPU and the model their records name.

**SMG as shipped (arm 8b).** `flatshare-smg.service` runs SMG 1.13.0's priority scheduler with its defaults. A vLLM worker behind its `openai` backend reports no capacity, so SMG sizes its pool at 64 slots, and its built-in reservations (system 32, interactive at least 128, default 10%) do not fit: it scales them down to system 19, interactive 39 and default 4, which leaves 2 slots for the bulk class, where the gateway sends background requests. Measured against `flatshare-bench mock-server`, 40 concurrent bulk requests went through 2 at a time, and the others wait in SMG's bulk queue (1,024 deep, 503 after 300 s). As shipped, arm 8b therefore caps the agents at 2 requests in flight; reservations that fit the pool take a `--priority-scheduler-config` file.

## Results

`flatshare-bench e2 report RUN_DIR... --out DIR` builds a frontier from any set of run directories, across campaigns too. It compares points only within a workload: the agents' corpus and the number of callers, the GPU and the model where they are not the frozen box's, and the warm-up turns that open each call where the points differ in them (W4's records with W5's). The discriminating scenario (`weka-x32-long`) and the calls-per-GPU points (4 and 6 callers) each get their own section of `frontier.md`, with the voice SLO they are read against (250 ms above voice alone with as many callers and warm-up turns), and their own figure (`frontier-weka-x32-long.svg`, `frontier-4-callers.svg`), beside `frontier.svg` for the standard one ([the figures](../../python/flatshare_bench/README.md#e2-points)). A point measured in several campaigns (W4's rounds of the discriminating scenario reuse w2c's and a9's arm files) is one configuration: the report keeps each run, gives the configuration's median and range, and places it on the frontier at its medians. `waterfall.svg` splits each configuration's voice turn into its stages (endpointing, the reply to its first sentence, TTS first audio, transport and playout), stacked to its mean V2V; `--waterfall POINT` picks the configurations it draws. `--dots FILE` adds a chart, `voice-p95.svg` and its phone layout: the configurations a TOML file names, each its V2V p95 against its workload's SLO beside the agents' tokens/s over the calls' first 240 s, with each one's share of the first row's. A figure of several GPUs gives each its rows under a `[[group]]` table with a `title`, and the `gpu` its points ran on where the GPUs ran the same arm files (`gpu = "A100-SXM4-80GB"`, as the figure names it), on one scale, each against its own voice alone's SLO. `make e2-w5-figure` draws docs/REPORT.md's chart from W5's [`figure.toml`](../results/2026-10-24-e2-w5/figure.toml), and `make e2-gpus-figure` the README's, of both GPUs, from the A100 run's [`figure.toml`](../results/2026-10-26-a100/figure.toml).

The repository keeps a compact record of each point, not its run directory: `flatshare-bench e2 export RUN_DIR... --out DIR` writes the few small files the report reads (about 15 kB a point, no credential and no home path) into `DIR/CAMPAIGN/POINT`, and the report gives the same tables and figures from them as from the run directories ([the compact record](../../python/flatshare_bench/README.md#e2-points)). E2's records are in [`benchmarks/results/2026-10-23-e2`](../results/2026-10-23-e2/README.md), and `make reproduce-e2` regenerates the report from them into `build/reproduce-e2` (`E2_REPORT=DIR` to choose), with the bench venv; `make reproduce-e2-w5` does the same for W5's records and `make reproduce-e2-a100` for the A100 run's:

```sh
python/flatshare_bench/.venv/bin/flatshare-bench e2 export $FLATSHARE_E2_RESULTS/w2c/* \
  --out benchmarks/results/2026-10-23-e2
make reproduce-e2
```

The run directories themselves, with the raw records the report does not need (the gateway's request log, AIPerf's exports, the metric snapshots, the worker's journal, the GPU's samples, the tools' logs), are an asset of the v0.3 release; W5's and FB's are the v1.0 release's `leaseholder-raw-records-w5.tar.gz` and `leaseholder-raw-records-fb.tar.gz`, named before the project's rename, and RS's the v1.3 release's `flatshare-raw-records-rs.tar.gz`.

## The demo video

The same caller on two engines while coding agents run: [`demo.py`](demo.py) renders two points measured with `flatshare-bench e2 run --save-audio`, which has the callers save each call's audio and the times of its turns ([`flatshare-voice bots --save-audio`](../../python/flatshare_voice/README.md#measurement-callers)). [`demo.campaign`](demo.campaign) measures two such points with its `save-audio` line: the frozen box and the PRs' configuration with a 48-token window in the discriminating scenario, on W5's round-1 sample of the agents:

```sh
benchmarks/e2/campaign.sh benchmarks/e2/demo.campaign
```

Then, on a workstation with the two run directories fetched into one directory, `make demo-video` renders the video to `build/flatshare-demo.mp4` (`DEMO_OUT`) and the README's animation to `docs/figures/e2-demo.webp`, with its dark theme and its phone layout (`e2-demo-dark.webp`, `e2-demo-narrow.webp`, `e2-demo-narrow-dark.webp`; `uv` installs the script's pinned numpy, matplotlib, Pillow, fontTools and imageio-ffmpeg, whose ffmpeg encodes; the video and the four animations take seven minutes on an Apple M5 Max laptop):

```sh
make demo-video DEMO=$FLATSHARE_E2_RESULTS/demo
```

It names the two configurations as the README's chart does, and reads W5's report (`benchmarks/results/2026-10-24-e2-w5/report/frontier.csv`) for the voice SLO and the closing card, and the A100's (`benchmarks/results/2026-10-26-a100/report/frontier.csv`, `--also`) for the card's second group, the same two configurations on the A100. The v1.0 release's `leaseholder-raw-records-demo.tar.gz` has the run directories of `demo.campaign`'s two points, measured on 2026-10-25 at v0.3-274 (`w5-disc-frozen-s24` and `w5-disc-pr-ab48-s24`, V2V p95 11,232 and 2,213 ms over both calls; they are not in the tables), the calls' audio among their files. The v1.0 release's 170-second video and the v0.3 release's 75-second one came from earlier versions of the renderer.

**What it shows.** An opening card names the calls and the engines (`--heading` is its heading). Then each frame is the dashboard the v1.0 demo drew, a panel for each call side by side: the baseline's call on the left in gray, the featured configuration's on the right in blue, each the point's first call (`--caller`). In each panel, a clock counts the wait from the end of the caller's speech to the reply's first audio and then gives the V2V the caller measured, with the wait against the SLO under it: the report's, voice alone's median V2V p95 with as many callers plus 250 ms (2.03 s), "over" it in orange as soon as the clock passes it. Beside the clock, each reply's V2V is a bar that grows while the caller waits, against the SLO's dashed rule, on one scale for both panels; the latest V2V stands over its bar. Under them, the turn under way runs on its time axis: the caller's line above the axis and the agent's reply below it, as their waveforms drawn as they play, the wait between them as a bar, and the SLO as a dashed rule after the end of the line. At the foot, the agents' tokens/s over the calls' first 240 s, the README's measure, on one scale for both panels, the featured one's as a share of the baseline's. Both calls play the same turns from `--first-turn` (by default the first measured one, after the call's warm-up turns): `--turns` of them, by default as many as fit in `--seconds` (180). Turn k of both starts at the same moment, so the same line is heard on both at once, and the call that is ahead waits in silence: only a caller's pause between turns is stretched, never a measured wait. The soundtrack is one call at a time, the caller and the agent mixed, the left call until the turn whose start is nearest the middle and the right call from it; the call heard is marked "sound on". A closing card gives both configurations over all the report's runs, the median of their V2V p95 and of the agents' tokens/s, as the README's chart draws them.

**How it is drawn.** The frames follow the docs' figures: STIX Two at the figures' four sizes, and the clock at twice a label's, on a layout 1120 units wide; the README's palette in `--theme` (light by default, or dark); the panels on the figures' gray ground inside dashed borders; the configuration to deploy in the saturated blue and the baseline in a comparison's gray. Each frame is drawn at twice its size and halved by a box filter, so type and hairlines stay crisp. Motion follows the calls: the playhead, the waveforms, the clock and the growing bars move linearly with their time. A text that changes leaves (ease-in-out, `cubic-bezier(0.77, 0, 0.175, 1)`, 0.24 s) before its successor arrives (ease-out, `cubic-bezier(0.23, 1, 0.32, 1)`, 0.4 s, from 0.96 of its size), a V2V once given holds at least 1.2 s, a turn's drawing leaves before the next turn starts, and nothing else moves. The video is 1920×1080 at 60 frames a second, H.264 (yuv420p, CRF 18, BT.709) with AAC sound. The README's animation (`--excerpt PREFIX`) is the same dashboard for the first `--excerpt-turns` turns (one), without the cards: silent, looping, every drawing leaving before the loop restarts, an animated lossless WebP at `--excerpt-fps` frames a second (60). It comes in each theme and in two layouts: the panels side by side, `--excerpt-width` pixels wide (1680, twice the 840 the README shows it at), and for a phone the panels one above the other, 420 units across like the figures' phone layouts (680 pixels, twice the 340 a phone shows it at). The README's `<picture>` shows the one of the reader's theme and screen.

`python/flatshare_bench/tests/test_demo.py` runs the renderer on a synthetic pair of calls, tones in the files `--save-audio` writes, and a report's frontier.csv: in CI the turns, the soundtrack, the summary, the motion's curves, and frames drawn headless at a low resolution, their size and count, the V2V each holds, and that no text leaves its room or overlaps another at any moment the calls change, with the bench venv's numpy, matplotlib and Pillow; and, marked integration since it fetches the script's dependencies, the script itself through `uv run` to an MP4 and the four WebPs (`uv run --extra test pytest -m integration tests/test_demo.py` in `python/flatshare_bench`). `tests/test_figures.py` checks the README's four WebPs: animated and looping, the same frames in each, the same size in both themes, each under 8 MB.
