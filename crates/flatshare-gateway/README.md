# flatshare-gateway

`flatshare-gateway` is the process in front of one vLLM engine. It carries Flatshare's request contract: who a request belongs to, which session and SLO class it has, and which engine inputs a client may not set. It relays responses byte for byte, cancels the engine request when the client leaves, and ingests lifecycle events. Its admission point runs `flatshare-core`'s admission policies: the E2 baselines it emulates, and the lifecycle policy (`policy = "lifecycle"`), which E2's arm 9 runs with make-room: KV headroom timed by lifecycle events, a prefill budget in the critical window, a realtime class that is never shed and degrades instead. What E2 measured of it is [below](#the-lifecycle-policy), and what its lifecycle timing could and could not do in [METHODS.md](../../docs/METHODS.md#what-lifecycle-timing-could-and-could-not-do). A deployment can cap every realtime reply without a policy (`realtime_max_tokens`).

It is a harness, not a general-purpose router: one upstream, loopback listeners, and nothing a stock proxy would not need besides the contract above. Its cost is measured below. The configuration to deploy ran behind it without an admission policy: the gateway set each request's priority from its SLO class ([PRODUCTION.md](../../docs/PRODUCTION.md#the-priorities)).

## Running

```sh
flatshare-gateway --config ~/.config/flatshare/gateway.toml
```

[`deploy/cyan/gateway.example.toml`](../../deploy/cyan/gateway.example.toml) is the configuration for cyan, [`deploy/cyan/systemd/flatshare-gateway.service`](../../deploy/cyan/systemd/flatshare-gateway.service) its unit, and [`flatshare-gateway.socket`](../../deploy/cyan/systemd/flatshare-gateway.socket) the socket unit that holds its listeners. The [runbook](../../ops/RUNBOOK.md#the-gateway) covers installing and checking it.

## What it does

- **Routes.** `POST /v1/chat/completions`, `/v1/completions` and `/v1/responses` are proxied with session, class and sanitization. The Responses API's `background` passes: vLLM 0.32 refuses it unless the engine runs with `VLLM_ENABLE_RESPONSES_API_STORE=1`, which the frozen box does not set, and with that set a background response would run detached, outside the admission point and the cancellation of a request whose client leaves. `GET /v1/models` is proxied with sanitized headers. `POST /v1/events` takes lifecycle events. `GET /health` and `/ready` are the gateway's own and need no key. `GET /metrics` (the gateway's metrics) and `GET /metrics/engine` (its engine's own `/metrics`, relayed, so that a scraper needs no route to the engine) need the metrics key on a TCP listener and nothing on a Unix socket ([Metrics and logs](#metrics-and-logs)). Any other path is 404, and a wrong method 405, both in OpenAI error format.
- **Listeners.** Any number of loopback TCP ports and Unix sockets; a TCP address beyond loopback is refused at start. The sockets systemd passes (`LISTEN_FDS`, socket activation; `flatshare-gateway.socket` on cyan) are served instead of new ones: each is matched to the `[[listen]]` entry of its address, an entry without one is bound as below, and a socket that no entry names stops the start before anything is bound, since nothing would accept on it. An inherited socket's file is the socket unit's, which removes it. A Unix socket the gateway binds itself is created with mode 0600 and removed at exit; a socket file that nobody accepts on (left by a crash) is replaced at start, while a live socket or a file that is not a socket is an error. Its directory must be the gateway's user's and closed to others (mode 700, as the units' `%t/flatshare`), or the start fails: bind() creates the file with the process's umask before its mode can be set, and meanwhile only the directory keeps other users from connecting. Once it has its listeners and is about to serve, the gateway sends `READY=1` to `NOTIFY_SOCKET` (sd_notify; its unit is `Type=notify`). A Unix listener may name a tenant for requests without a known key. TCP listeners may not, because every user of the host can reach loopback.
- **Tenants and keys.** `Authorization: Bearer <key>` is hashed with SHA-256 and compared with every configured digest in constant time; the loop never exits early, so timing reveals neither which key matched nor how much of a digest did. A known key selects its tenant, on any listener. Otherwise the request belongs to the listener's tenant, or gets 401. The voice worker's OpenAI client sends a placeholder key, so on the voice socket an unknown key also means the socket's tenant.
- **Sanitization.** From every request: the engine-control headers (`X-Vllm-Priority`, `X-SMG-Priority`, `X-data-parallel-rank`, and `X-Session-ID` unless the tenant is trusted), `X-Request-Id`, every `X-Flatshare-` header, `X-Claude-Code-Session-ID`, `Authorization`, and hop-by-hop headers, including those named in `Connection`. From every JSON body: vLLM 0.32's `session_id`, `priority`, `kv_transfer_params`, `ec_transfer_params`, `cache_salt`, `request_id` and `vllm_xargs`, and SGLang 0.5.22's `rid`, `extra_key`, `session_params`, `custom_labels` and routing fields (`routed_dp_rank`, `data_parallel_rank`, `disagg_prefill_dp_rank`, `bootstrap_host`, `bootstrap_port`, `bootstrap_room`) (`flatshare_proto::headers`). Only the top level of the body is parsed; values are copied through as raw JSON, and keys are compared after unescaping. Each removal of an input the client may not control is counted in `flatshare_gateway_sanitized_total`.
- **What it sets.** `X-Session-ID` (the resolved session), `X-Request-Id` (a fresh id, also returned to the client), the body `cache_salt` (the first 32 hex digits of HMAC-SHA-256 of the tenant's name, keyed by the secret in `cache_salt_secret_file`), and the class's priority in the signals `upstream_priority` lists: `X-Vllm-Priority` by default (realtime 0, interactive 1, background 2, as vLLM's priority scheduling reads it), the same number as the body's `priority` (SGLang's), or `X-SMG-Priority` (`system`, `interactive` and `bulk`, for SMG's priority scheduler). Every proxied inference response carries `X-Flatshare-Session-ID`.
- **Sessions.** The first present source in [PROTOCOL.md](../../docs/PROTOCOL.md#sessions) order: a trusted tenant's `X-Session-ID`, `X-Claude-Code-Session-ID`, the body's `prompt_cache_key`. A trusted tenant's valid session id is used as it is. Any other value becomes `h-<first 32 hex of SHA-256(tenant, NUL, value)>`: every source of an untrusted tenant, so that it cannot name another tenant's session (its token estimates, its turn state, the session id the engine sees), and a value that is not a valid session id. With no source the gateway mints `m-<32 random hex>`.
- **Classes.** A trusted tenant may ask for one with `X-Flatshare-Class` (an unknown value is 400); otherwise the tenant's `default_class` applies. A class stricter than the tenant's `max_class` is clamped to it and counted.
- **Admission.** Under an `[admission]` policy, a request whose session and class are resolved waits there until the policy admits it, and is refused when its queue is full or its wait reaches `queue_timeout_s` ([Admission](#admission)). Nothing polls: a waiting request learns of its admission on a channel. An admitted request holds its place until its response ends or its client leaves; a client that leaves while it waits gives its place up at once. Under the lifecycle policy the admission point also follows each realtime session's turn, from lifecycle events and from the session's realtime requests.
- **An engine that restarts.** A request that finds the upstream broken (no connection, or one that closes before the response headers) gets 502 `upstream_unavailable` and starts a probe of the engine's `/health`: at once, then every second until it answers. While the probe fails, requests get 503 `upstream_not_ready` with `Retry-After: 1` at once, without going upstream, and `/ready` answers 503; the probe that answers lets requests go upstream again. An engine restart (106 s from the kill to the first success in the final build's drill, 92 s of it the engine's warm start; [the drills](../../docs/BENCHMARKS.md#failure-drills)) is then one 502 and a stream of cheap 503s that tell clients to come back, instead of a 502 per request that each reached for a dead engine (and, through the tunnel, opened a session on its node). One connection that breaks on an engine that serves makes no request wait: the probe answers at once. A timeout is no reason to probe: the engine is slow, not gone.
- **Relay.** A pump task reads the upstream body into a bounded channel (`stream_buffer_frames`, 64 by default) that the client's response body drains. A full channel stops the pump from reading the upstream, so a slow client slows the engine's socket, not the gateway's memory. If the channel stays full for `stall_timeout_s`, the pump aborts the upstream request and the client's response ends with an error. When the client leaves, its response body is dropped, the pump sees the channel close and drops the upstream body at once, which closes the upstream connection; vLLM aborts a request whose client disconnects. A client that leaves before the response headers is handled the same way: hyper drops the handler, and with it the upstream request. A response cut short, by a stall, by the upstream, by a shed or by a drain, never ends cleanly, so the client cannot mistake it for a complete one. When the upstream breaks off an event stream (the engine died, or its connection broke), the gateway first sends the error event of vLLM's own streams, `data: {"error": {"message": "the upstream stream broke off: ...", "type": "upstream_unavailable", "param": null, "code": 502}}`, after a blank line that ends any partial event, and then aborts the stream, so that a client that reads events learns why and one that ignores them still sees a broken stream. hyper drops the bytes it has not written when a body errors, so the abort waits one poll after the last frame.
- **Usage.** Token usage is read from non-streaming JSON bodies and from SSE `data:` lines, for all three APIs (`prompt_tokens`/`input_tokens`, `completion_tokens`/`output_tokens`, `cached_tokens`). Only lines that carry a non-null `usage` or `finish_reason` are parsed. The stream itself is never rewritten.
- **Lifecycle events.** `POST /v1/events` accepts one `flatshare_proto::LifecycleEvent` or a JSON array of them, from trusted tenants only (403 otherwise). A batch is validated in full before any of it is recorded; an unknown `type` is 400 with the event's index. Events are deduplicated by `(tenant, source, event_id)` within a window of `event_dedup_capacity` ids and `event_dedup_ttl_s`. New events go to the admission point, where the lifecycle policy follows the realtime sessions' turns by them, and then to an `EventSink`; the `LogSink` writes one log line per event. The answer is 202 `{"accepted": n, "duplicates": m}`.
- **Lifecycle.** SIGTERM or SIGINT stops the listeners, lets in-flight requests finish for up to `drain_timeout_s`, except background ones, which it cuts `background_drain_s` (5 s) into the drain (a stream with the `draining` error event, `data: {"error": {..., "type": "draining", "param": null, "code": 503}}`, and an abort; a request without a response yet with 503 `draining` and `Retry-After: 1`), removes the socket files it bound and exits 0. SIGHUP reloads without a gap: the gateway starts its successor from the binary at its own path and with its own arguments, so from the build and the configuration on disk, with its listening sockets from fd 3 on (`LISTEN_FDS`); the successor takes them instead of binding, tells systemd that it is the unit's main process and ready (`MAINPID=`, `READY=1`), and sends SIGTERM to its predecessor, which drains as for a stop. Both accept on the same sockets until then, so no connection is refused or waits. A successor that exits (a broken configuration, say) or does not take over within 10 s changes nothing: the old process serves on, and `systemctl --user reload flatshare-gateway` fails ([`deploy/bin/flatshare-gateway-reload`](../../deploy/bin/flatshare-gateway-reload) waits for the unit's main process to change). A reload keeps the listeners: a change to `[[listen]]` takes a restart, with the socket unit's. Under socket activation (`flatshare-gateway.socket` on cyan) the sockets outlive a stop and a crash as well: the connections made until the next gateway serves wait in the backlog, for the drain on a restart and about a second after a crash, instead of being refused. While a reload's predecessor drains, each process has its own admission point, which does not see the other's requests; the predecessor keeps its realtime and interactive requests, and its background ones for `background_drain_s` at most. A configuration error exits 2 with the file and the cause; a listener that cannot bind, or an inherited socket that no listener names, exits 1.

## What it does not do

- Leases, prefetch or a recompute ledger: the lease design was not pursued ([ADR-0006](../../docs/adr/0006-the-engine-change-carries-the-realtime-tier.md)). Nor admission for interactive requests by predicted time to first token: the lifecycle policy does not hold interactive requests.
- Retries, or balancing requests over several engines. The placement of sessions on several GPU nodes that E2's two-node points were built for (`[nodes]`, `[placement]`, `POST /v1/sessions`) never ran, since no second GPU was free before v1.0, and is kept on the `two-node` branch.
- TLS. Every listener binds loopback or a private socket, and the upstream is a tunnel's socket or a loopback port.
- The Anthropic Messages API: a translating layer in front of the gateway, such as agentic-api, calls its OpenAI-compatible routes.
- Inferring `turn_started` and `turn_finished` from traffic. The finish reason is logged per request.
- The Responses API's stop reasons (its usage is read).
- What a production gateway would need beyond this harness:
  - a bound on the request bodies it holds in all: each request holds its body, up to `max_body_bytes`, while it waits at the admission point (up to `queue_limit` a class) or is sent, and nothing bounds the requests in flight or the connections;
  - timeouts on reading a request body and between upstream frames: a client that trickles its body, or an engine that stops in mid-stream without closing, holds its place, and under a policy its admission slot, until the client leaves;
  - cost bounds: nothing caps `n`, nor `max_tokens` beyond `realtime_max_tokens` and degrade's cap on realtime replies;
  - a client that resends: a draining gateway closes its idle keep-alive connections, as every HTTP/1.1 server does, and a request sent on one at the moment it closes gets no answer. It never reached the gateway, so sending it again on a new connection is safe: the voice worker's LLM requests get one more try (LiveKit's `max_retry=1`, `flatshare_voice.worker`), and a client without one sees the error.

## Configuration

Unknown keys are errors, so a misspelled setting fails at start instead of silently taking its default.

| Key | Default | Meaning |
|---|---|---|
| `upstream` | required | The engine: `http://host:port`, or `unix:` and the absolute path of its socket, such as a tunnel's (`unix:/run/user/1007/flatshare/phastform-engine.sock`). Either is spoken to over HTTP/1.1 with pooled connections |
| `upstream_idle_timeout_s` | 4 | How long an idle upstream connection is kept for reuse. Keep it below the engine's keep-alive (`VLLM_HTTP_TIMEOUT_KEEP_ALIVE`, 5 s by default), or a request can go out on a connection the engine is closing |
| `upstream_priority` | `["vllm-header"]` | Where the class's priority goes upstream: any of `"vllm-header"`, `"body"` and `"smg-header"`. The empty list sends none, as a plain client does: E2's stock arm. vLLM 0.32's FCFS scheduler ignores priorities rather than rejecting them |
| `cache_salt_secret_file` | required | An absolute path: a file of 32 random bytes in hex that only its owner may open (mode 600), which `deploy/cyan/install.sh` writes once. It keys every tenant's `cache_salt`, so that a client which reaches the engine directly cannot compute another tenant's salt from its name. A missing or unreadable file, one other users may open, or one that holds anything else stops the gateway at start. A new secret changes every salt, which orphans every tenant's prefix cache |
| `metrics_key_file` | required with a TCP listener | An absolute path: a file of one key on one line that only its owner may open, which `deploy/cyan/install.sh` writes once. `GET /metrics` and `/metrics/engine` on a TCP listener need it as `Authorization: Bearer <key>` (401 otherwise): every user of the host reaches loopback, and the metrics name the tenants and their traffic. The gateway keeps its SHA-256 and compares in constant time, as for tenants' keys. On a Unix socket, whose file mode keeps other users out, no key is asked for |
| `max_body_bytes` | 33554432 (32 MiB) | Larger request bodies get 413 |
| `realtime_max_tokens` | none | The cap on every realtime reply, in tokens, with or without an admission policy: each of the body's `max_tokens`, `max_completion_tokens` and `max_output_tokens` above it (or not a count) is lowered to it, and a body with none of them gets the route's own, as degrade caps a reply. Under the lifecycle policy a degraded reply gets the lower of the two caps |
| `stream_buffer_frames` | 64 | Frames buffered between the upstream and a client |
| `stall_timeout_s` | 30 | How long that buffer may stay full before the stream is aborted |
| `first_byte_timeout_s` | 600 | How long to wait for the upstream's response headers before 504; for a request preempt-resubmit may preempt, for its first body byte |
| `drain_timeout_s` | 30 | How long a shutdown waits for in-flight requests |
| `background_drain_s` | 5 | How far into a drain background requests go on: then a background stream ends with the `draining` error event and an abort, and a background request without a response yet, or still waiting at the admission point, gets 503 `draining` with `Retry-After: 1`, so that its client sends it again to the gateway that serves next. Realtime and interactive requests have the whole `drain_timeout_s`. From 0 (cut as the drain starts) to `drain_timeout_s` |
| `event_dedup_capacity` | 100000 | Lifecycle-event ids remembered for deduplication |
| `event_dedup_ttl_s` | 600 | How long an event id is remembered |
| `log_format` | `"text"` | `"text"` or `"json"` (one object per line) |
| `log_level` | `"info"` | `error`, `warn`, `info`, `debug` or `trace` |

Each `[[listen]]` entry sets exactly one of `tcp = "127.0.0.1:18080"`, a loopback address, or `unix = "/absolute/path.sock"`, and a Unix entry may set `tenant`. Each `[tenants.<name>]` table (names from `[A-Za-z0-9._-]`) sets:

| Key | Default | Meaning |
|---|---|---|
| `keys_sha256` | `[]` | Hex SHA-256 digests of the tenant's API keys; the keys never appear in the file. A tenant with no keys must be named by a listener |
| `trusted` | `false` | May set `X-Session-ID` and `X-Flatshare-Class`, and post lifecycle events |
| `default_class` | `"interactive"` | The class of requests that do not choose one |
| `max_class` | `default_class` | The strictest class the tenant may use |

The `[admission]` table sets the admission policy. A key that belongs to other policies than the chosen one is an error, like an unknown key, and so, under `lifecycle`, is a key that no mechanism switched on reads.

| Key | Default | Policies | Meaning |
|---|---|---|---|
| `policy` | `"none"` | | `"none"` (every request goes upstream at once), `"static-cap"`, `"token-reservation"`, `"flow-control"`, `"preempt-resubmit"` or `"lifecycle"` (`"leaseholder"` in arm files from before the project's rename) |
| `background_max_in_flight` | required | `static-cap` | Background requests in flight at most |
| `pool_tokens` | 36400 | `token-reservation`; `lifecycle` with `headroom` or `degrade` | The KV pool in tokens; the default is the frozen box's |
| `reserved_tokens` | required | `token-reservation` | Pool tokens background requests leave free; less than `pool_tokens` |
| `ceilings` | required | `flow-control` | `{ realtime = 16, interactive = 12, background = 8 }`: each class is dispatched while fewer requests than its ceiling are in flight. The ceilings must not increase from realtime to background |
| `headroom` | `true` | `lifecycle` | Keep KV headroom free for the armed realtime sessions |
| `headroom_tokens` | required with `headroom` or `degrade` | `lifecycle` with `headroom` or `degrade` | The KV of one realtime turn, its prompt and its reply: the headroom kept per armed session, and what a realtime request must find free not to be degraded. Less than `pool_tokens` |
| `trigger` | `"onset"` | `lifecycle` with `headroom` | What arms the headroom: `"onset"`, the user's speech onset, until the reply's first audio; `"request"`, the critical window alone, from the end of the user's turn or the realtime request, whichever comes first |
| `throttle` | `true` | `lifecycle` | Budget the background prefill admitted in a critical window |
| `critical_prefill_budget_ms` | required with `throttle` | `lifecycle` with `throttle` | The predicted prefill time the background requests admitted in one critical window may take in all; 0 admits none |
| `max_num_batched_tokens` | 512 | `lifecycle` with `throttle` | The engine's `--max-num-batched-tokens`, in whose steps the throttle prices a prefill |
| `degrade` | `true` | `lifecycle` | Cap the reply of a realtime request that finds less than `headroom_tokens` free |
| `degrade_max_tokens` | required with `degrade` | `lifecycle` with `degrade` | That cap, in tokens |
| `max_defer_s` | 10 | `lifecycle` with `headroom` or `throttle` | How long a background request may be deferred; it is then admitted regardless. Longer than an E2 caller's turn is armed, about 4 s |
| `state_timeout_s` | 10 | `lifecycle` | How long a realtime session stays in a state of its turn that no event moves it on from. Longer than any state of an E2 caller's turn |
| `queue_limit` | 1024 | all but `none`; `lifecycle` with `headroom` or `throttle` | Requests each class's queue holds; one more gets 429. The lifecycle policy queues only background requests |
| `queue_timeout_s` | 60 | all but `none` and `lifecycle` | How long a request may wait before it gets 503. The lifecycle policy refuses no request for its wait |

## Admission

The admission point, the policies it runs, the realtime sessions' turns that the lifecycle policy follows, and their configuration and metrics are E2's harness (`src/harness/`): a gateway without an `[admission]` policy runs none of it, and the proxy reaches it only through a request's admission ticket. `realtime_max_tokens` is not the harness's: it caps realtime replies in the proxy, with or without a policy. The admission point is between resolving a request (tenant, sanitization, session, class) and the upstream request. `flatshare_core::admission` decides, from the order of events alone: a request's arrival, its response's first byte, its departure, and under the lifecycle policy the realtime sessions' turns and the end of a deferral. The gateway does the waiting, its timeouts and the cancellation. A policy holds some classes; requests of the others go upstream at once. Within a class, waiting requests are admitted in arrival order, and none goes ahead of a waiting request of a stricter class.

The first four policies are E2's baselines, the simple answers an operator would try and what routers ship, run here so that every arm has the same engine, clients and measurement; the fifth is [the lifecycle policy](#the-lifecycle-policy). The emulations of routers say what they reproduce and what they do not.

- **`static-cap`** (E2 arm 6): at most `background_max_in_flight` background requests in flight; the rest wait. Realtime and interactive requests are not held. It is a background concurrency limit, as an operator would put one in front of the engine.
- **`token-reservation`** (E2 arm 6, the equal-size static reservation): a background request is admitted while the estimated tokens of the background requests in flight, its own and `reserved_tokens` fit in `pool_tokens`, so that the reservation stays free for realtime and interactive requests, which are not held. A request too large to fit beside the reservation is admitted once no other background request is in flight, so it cannot hold up the queue for good.
  - *The estimate.* There is no tokenizer. A request's prompt tokens are its session's last reported `prompt_tokens` plus the growth of the body since that request (an agent's next turn resends the conversation and adds to it), at 4 bytes per token. A body smaller than the session's last is another conversation (a subagent shares its parent's session) or a compacted one, and is estimated as for a session without a report: its whole body at 4 bytes per token. The body is the one sent upstream, after sanitization. A session is its tenant's: two tenants that name the same session id have a session each.
  - *The sessions remembered.* The admission point keeps what it knows of a session, its last report and, under the lifecycle policy, its turn, in one table of at most 4,096 sessions. A new session that finds the table full takes the place of the session seen longest ago that is not in a turn, and is not remembered only while every session is in one. Untrusted tenants' sessions take at most half the table: each `prompt_cache_key` of an untrusted tenant is a session of its own, and a flood of them takes the places of the trusted tenants' sessions seen longest ago only until untrusted sessions hold half, so the trusted tenants keep up to half the table.
  - *Its error on the replay.* On the W2 operating points, the agent replay at 8, 16 and 24 agent sessions (415 to 1,521 requests), the estimate is off by 0.4 to 0.5% of all prompt tokens, against 1.9 to 2.2% for bytes / 4 alone. Of the requests of 1,000 tokens or more, 90% are within 1.3 to 1.6% (bytes / 4: 3.4 to 4.5%), 99% within 4.1 to 5.8% (4.5 to 6.5%) and all within 9.4% (8.2%). AIPerf's synthetic prompts run at 3.9 to 4.0 bytes per token, close to the estimate's 4; the session's report leaves only a turn's growth to that rate, so text further from it moves the estimate less than it moves bytes / 4. `cargo run --release -p flatshare-core --example estimate_error -- RUN/aiperf/profile_export.jsonl...` replays an export as the gateway would see it; its byte counts are AIPerf's, headers included, where the gateway counts the body alone.
  - *What it leaves out.* The estimate counts a request's prompt, not the KV it holds as it decodes, and requests that share a prefix share its blocks in the engine. The sum is a proxy for the pool's use, not a measurement of it.
- **`flow-control`** (E2 arm 8, llm-d's flow control, emulated): each class is a priority band, and the bands are dispatched strictly, a stricter band's waiting requests always first. `ceilings` holds the bands back: a request goes upstream while the requests in flight, of every class, are fewer than its class's ceiling, and since the ceilings fall from realtime to background, background is held back first as the engine fills. Within a band, requests go in arrival order. A realtime or interactive request blocked by its ceiling sheds the newest background requests in flight, as many as it takes, if that is enough to let it in. Their upstream requests are cancelled at once, and their clients get 429 `shed`, or an error that ends a stream already begun. When shedding is not enough, because realtime and interactive requests fill the ceiling, a realtime request waits like any other and can be refused at the queue limit or timeout, which the lifecycle policy never does to realtime ([ADR-0003](../../docs/adr/0003-realtime-is-never-shed.md)).
  - *What it reproduces.* llm-d v1.0's flow control with its priority-holdback usage limit and in-flight eviction (`flowControl.enableEviction`): strict priority bands, a ceiling per band that holds the lower priorities back as utilization rises, and the eviction of sheddable requests in flight when stricter demand is blocked, which their clients see as HTTP 429.
  - *What it does not.* Utilization is the number of requests in flight, where llm-d reads a saturation detector over the engine's metrics, so the ceilings are counts rather than fractions of saturation. llm-d orders a band by an SLO deadline from the `x-llm-d-slo-ttft-ms` header; here the requests of a band share one class, and with one target per class, earliest deadline first is arrival order. Eviction takes effect at once and picks the newest background request, the one with the least work done, where llm-d paces evictions behind a confirmation gate (the evicted streams end, then a grace period; at most 2 per decision). Fairness between the flows of a band, and llm-d's limits on queued bytes, are left out.
- **`preempt-resubmit`** (E2 arm 8, a router's abort-and-resubmit of background work on a voice turn, with SMG's rule that only a request without a first byte may be preempted): a realtime arrival preempts the background requests in flight that have no first body byte yet. Their upstream requests are dropped, which aborts them in the engine, and they wait at the front of the queue; background requests that arrive meanwhile wait behind them. Once every realtime request has its first byte, or has ended, they are all sent again. Since a background request can be preempted until its first byte, the gateway holds its response back until then: the client sees nothing of a dropped attempt and gets one response, whose first byte comes later. For a streaming response this delays only the headers, and the first-byte timeout covers each attempt to its first byte. A response already streaming is never preempted, and interactive requests are not held.
  - *What it counts.* Resubmissions, and the prompt tokens of the dropped attempts, estimated as for token-reservation: an upper bound on the prefill they discarded, since an attempt may be dropped while it still waits in the engine, and the blocks it finished stay in the prefix cache for its resubmission.
  - *What it does not reproduce.* SMG preempts to free a concurrency slot for a higher class, and answers the preempted request 503 with `Retry-After`, leaving the retry to the client; E2 runs SMG itself for that (arm 8b). This emulation preempts to clear the voice turn's prefill whatever the slots, and resubmits on the client's behalf.

### The lifecycle policy

**The lifecycle policy** (`policy = "lifecycle"`, or `leaseholder` as arm files spelled it before the project's rename) is what E2's arm 9 runs with make-room. Realtime requests go upstream at once and are never queued or refused ([ADR-0003](../../docs/adr/0003-realtime-is-never-shed.md)); background requests yield to the realtime sessions' turns; interactive requests are not held. `flatshare-core` decides from how many realtime sessions are in each state of their turn; the gateway keeps the states and the clocks.
- **Realtime sessions.** Accepted lifecycle events move a session, keyed by its session id, through `idle`, `user_speaking` (`user_speech_started`), `critical` (`user_turn_ended`), `playback` (`playback_started`, the reply's first audio) and back to `idle` (`playback_ended`). `interrupted` is the user speaking again, and `session_closed` forgets the session. A realtime request also puts its session in `critical`: LiveKit's preemptive generation sends it before the end of turn is decided.
  - *Lost or reordered events.* An event moves its session to the event's state whatever the state was, in the order the gateway receives events, and every state but `idle` ends after `state_timeout_s` without an event or a request, counted. A lost event holds a session at most that long.
  - *Without events.* A session that has posted none (its client sends none, or the voice worker's events are off) is `critical` while a realtime request of it is in flight, and the request's end ends it; with events, the reply's first audio does.
  - The sessions' turns are kept in the admission point's table of sessions ([the sessions remembered](#admission)), which forgets no session in a turn: a new session takes the place of the idle one seen longest ago, and is not followed only while every session is in a turn.
- **Headroom** (`headroom`, `headroom_tokens`, `trigger`). While sessions are armed, a background request goes upstream only if the estimated tokens of the background requests in flight and its own leave `headroom_tokens` of the pool free for each armed session. The others wait: deferring new background turns lets the running ones finish, and their KV parks in the write-through CPU tier. A session is armed from speech onset to the reply's first audio (`user_speaking` and `critical`) with `trigger = "onset"`, and in its critical window alone with `"request"`. The estimate is token-reservation's.
- **Critical-window throttle** (`throttle`, `critical_prefill_budget_ms`, `max_num_batched_tokens`). From the first session's entry into `critical` until no session is, the background requests admitted share `critical_prefill_budget_ms` of predicted prefill time, and the rest wait for the window to end. A request's prefill is priced by `flatshare-core`'s step model: the steps a lone prefill of its new tokens (those beyond its session's last reported prompt) takes after the rest of the prompt, in steps of `max_num_batched_tokens`. On the frozen box, 512 tokens after a 30,000-token context take 269 ms and after none 38 ms, a difference a token budget cannot see. The fit is compiled in: the gateway always prices by the frozen box's (`flatshare_core::StepCost::frozen_box`), and no configuration key takes another, so a different engine or GPU needs a fit of its own, from `flatshare-sim`'s `scripts/fit_step_cost.py`, built into `flatshare-core`.
- **Degrade** (`degrade`, `degrade_max_tokens`). A realtime request that arrives while the background requests in flight leave less than `headroom_tokens` of the pool free is still admitted at once, with its reply capped. In its body, each of `max_tokens`, `max_completion_tokens` and `max_output_tokens` above the cap (or not a count) is lowered to it, and a body with none of them gets the route's own: `max_completion_tokens` for Chat Completions, `max_tokens` for Completions, `max_output_tokens` for Responses. With `realtime_max_tokens` set too, a degraded reply gets the lower cap.
- **Aging** (`max_defer_s`). A background request deferred that long is admitted regardless, so agents are never starved. It is also what admits a request whose estimate alone is more than the headroom leaves (`oversize`): an agent context near 32k tokens while several sessions are armed, which the 36,400-token pool holds only at 90% occupancy.
- **What each switch ablates in E2.** `headroom = false`: no KV headroom in the gateway, as with only the engine's class-aware reserve (the make-room variant) or none; `trigger = "request"`: the headroom from the end of the turn instead of from speech onset; `throttle = false`: background prefill unbudgeted in the critical window; `degrade = false`: realtime replies never capped. With all three off the policy holds nothing back and only follows the sessions.
- **What it counts.** Background requests deferred, by what held them back when they arrived (the headroom first, then the critical window), and how long they waited; aged admissions, oversize ones apart; degraded replies; sessions by state, and state timeouts. And *false alarms*: armings of the headroom that no realtime request of the session followed before the session left the armed states (by an event, a timeout or its close), with the token-seconds of background work the headroom held back meanwhile, the estimated tokens of the background requests waiting for it integrated over time. While other sessions are armed as well, that cost is an upper bound.
- **What it leaves out.** Interactive requests are not held. The headroom works from the gateway's estimate of the background requests' KV, as token-reservation does (their prompts, not their decode growth, with shared prefixes counted for each request), where the engine's own reserve counts blocks exactly. No event says that speech ended without a turn, so a false alarm keeps its headroom until `state_timeout_s`.
- **What E2 measured** (2026-10-23, its discriminating scenario). With the change, arm 9 without the headroom, the throttle or the events, or with `trigger = "request"`, lands within the spread of arm 9's own runs, and on the stock engine this policy leaves voice where stock vLLM does; why its mechanisms could not act there is in [METHODS.md](../../docs/METHODS.md#what-lifecycle-timing-could-and-could-not-do). The tail depends on degrade, since the engine's budget cap protects only a reply's first 16 tokens ([EXPERIMENTS.md](../../docs/EXPERIMENTS.md#e2-voice-under-agent-load)).

## Errors

Errors the gateway generates use OpenAI's format, `{"error": {"message", "type", "code"}}`, and carry `X-Request-Id`. Responses from the engine pass through unchanged. An event stream the upstream breaks off after its headers ends with an error event instead ([Relay](#what-it-does)).

| Status | `code` | When |
|---|---|---|
| 400 | `invalid_class`, `invalid_json`, `invalid_event`, `unreadable_body` | An unknown `X-Flatshare-Class`; a body that is not a JSON object, or that cannot be read; an invalid lifecycle event |
| 401 | `invalid_api_key` | No known key, on a listener without a tenant; for `/metrics` and `/metrics/engine` on a TCP listener, no metrics key |
| 403 | `untrusted_tenant` | Lifecycle events from an untrusted tenant |
| 404, 405 | `not_found`, `method_not_allowed` | Any other route or method |
| 413 | `body_too_large` | A body over `max_body_bytes` |
| 429 | `queue_full`, `shed` | The request's class queue at the admission point is full (`queue_limit`); a background request shed by flow control before its response began. The `type` is `rate_limit_error` |
| 502 | `upstream_unavailable` | The engine could not be reached, or closed the connection before answering; for `/metrics/engine`, it did not answer within 10 s |
| 503 | `queue_timeout`, `upstream_not_ready` | Not admitted within `queue_timeout_s`; the engine is not ready (a request found it broken and its `/health` has not answered since), with `Retry-After: 1` |
| 504 | `upstream_timeout` | No response headers within `first_byte_timeout_s` |

## Design notes

- **Upstream client: hyper-util's pooled client rather than reqwest.** The request is already an `http::Request` with a sanitized `HeaderMap`, so it goes upstream without conversion, and the response body is hyper's `Incoming`, read frame by frame. reqwest wraps the same client and would add a URL parse, header conversions and redirect handling per request, none of which a fixed loopback upstream needs. Idle upstream connections close after `upstream_idle_timeout_s`, before the engine's keep-alive closes them under a request. With vLLM's default of 5 s, a voice call, whose turns are often more than 4 s apart, opens a new upstream connection for most turns; on cyan the engine keeps connections for 60 s and the gateway for 55 s. A `unix:` upstream is the same client with a connector that opens the socket for every new connection; the pool, its idle timeout and the first-byte timeout are the same as over TCP.
- **Request ids** are a random 64-bit prefix chosen at start and a counter. They need to be unique, not unpredictable (a client cannot set them), and they cost no system call. Minted session ids use 128 random bits.
- **The overhead metric starts when the request body is complete and ends at the first poll of the upstream request body,** which hyper does on a checked-out connection as it writes the request, so connection checkout is included. The body's arrival is timed separately (`flatshare_gateway_request_body_seconds`): a client that sends its body some time after its headers would otherwise have its own delay counted as the gateway's.

- **Streamed chunks cost about the same as the bare hop:** 65 against 61 µs at p50 for one stream.

## Tests

`cargo test -p flatshare-gateway` runs in a few seconds and needs only loopback. The integration tests (`tests/gateway/`) put the gateway between a raw HTTP/1.1 client and an in-process mock engine that records each request, streams SSE with set delays, holds a request's answer until the test releases it, and reports when its response body (or a pending handler) is dropped. They check, grouped by what each part holds to:

- **The request contract:** header and body sanitization; each upstream priority signal; session order, hashing and minting; classes and clamping; per-tenant cache salts; 401, 400, 413, 404 and 405.
- **The relay:** byte-exact SSE relay with usage; a client leaving mid-stream (the engine's body is dropped though the engine sends nothing more) and before the headers; a stalled reader, aborted after the stall timeout and ending in an error; an event stream the upstream breaks off (its bytes, then the error event, then an abort; a break inside an event ends that event first; a JSON body gets no event); 502 and 504.
- **The upstream:** an engine on a Unix socket (requests and streams, one pooled connection until the idle timeout, cancellation, a socket nobody serves); an engine that restarts (one 502, then 503 with `Retry-After` without going upstream until its `/health` answers, then requests again); a connection that breaks on an engine that serves (no request waits).
- **Events and metrics:** events; the metrics exposition, each policy's series and none without one; `realtime_max_tokens`, which caps every realtime reply and no other without a policy.
- **Sockets and the process:** the Unix socket (stale file, mode, live-socket refusal, a directory others can enter refused, cleanup); a graceful drain and its cut of background requests (a stream ends with the `draining` event at its grace, a request without a response and one still queued get 503 with `Retry-After`, one that ends in time is not cut, and realtime and interactive streams finish whole); inherited sockets (a connection made before the gateway exists is served, an inherited socket's file stays, a listener without one is bound, and an unnamed one is refused before anything binds); the binary as systemd runs it, on its `LISTEN_FDS` sockets with `READY=1` to a `NOTIFY_SOCKET`, and its reload (a successor takes over with `MAINPID=` while a voice turn finishes whole, an agent turn is cut at its grace and a request every 20 ms on each socket succeeds; a successor that cannot start changes nothing; a gateway that bound its own sockets leaves their files to its successor).
- **The admission point's baselines:** a static cap that holds while realtime passes, its first-in, first-out queue, 429 at the queue limit, 503 at the queue timeout, and a waiting client that leaves and gives its place up; token reservation priced from a session's last usage, the usage of one tenant's session pricing no other tenant's of the same id, and the trusted tenants' usage kept through an untrusted tenant's flood of 4,096 sessions; flow control's strict band order with arrival order within a band, and the shedding of the newest background request for a blocked realtime one, before its response (429, the engine's request dropped) and in the middle of a stream (an error); preempt-resubmit, where a background request preempted before its first byte, waiting for its response headers or in prefill behind them, is dropped at the engine and sent again after the realtime request's first byte, background arriving meanwhile waits too, the client gets one whole response, and a response already streaming is never preempted.
- **The lifecycle policy**, whose tests post events to `/v1/events` and then send requests: a background request deferred while a session is armed and sent when its reply's first audio is posted, with the realtime request going past it; the critical window's prefill budget, and a lost `playback_started` that `playback_ended` makes up for; aging, oversize and not; a degraded reply's `max_tokens` lowered in the body the engine receives, and to the lower of degrade's cap and `realtime_max_tokens` with both; a cough's arming that times out, counted as a false alarm with its token-seconds; a realtime request without events that is its own critical window; a new session in a full table taking the place of one idle session; realtime requests that go while the background queue is full. Breaking the headroom, the throttle, degrade, the oversize count or aging in `flatshare-core` fails at least one of them.

The unit tests pin:

- **The configuration rules:** each admission policy's own keys and defaults; the lifecycle policy's switches, the mechanisms each of its keys needs on, and its old name; `realtime_max_tokens`; every arm file's `[gateway]` table over the deploy example.
- **The realtime sessions:** their states, timeouts and false alarms, and their place in the session table.
- **The session table:** its bound, its untrusted half and its tenants.
- **The rest:** the reply cap a degraded request's body gets; the cache salts and the checks of their secret's file; hashed session ids; the constant-time key match at every position; the deduplication window; the SSE scanner under every split of a stream; the metric series a proxied request updates, each resolved at start to its family's series of its labels.
