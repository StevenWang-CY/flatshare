# Runbook

How to deploy, check, operate and recover the Flatshare hosts, for whoever operates the box and its control host; a deployment on other hardware, or on one host, follows [HARDWARE.md](../docs/HARDWARE.md). Every service runs as a `systemd --user` unit. Lingering is enabled on each host, so units survive logout and start at boot.

| Host | Units | Listeners |
|---|---|---|
| Phastform (GPU) | `flatshare.target` → `flatshare-stt`, `flatshare-tts`, `flatshare-engine` | No TCP: the engine, STT and TTS on Unix sockets in `/run/user/$UID/flatshare/` (`engine.sock`, `stt.sock`, `tts.sock`), a directory only the deployment's user may enter. Variant `sglang` serves 127.0.0.1:8000 too, behind `engine.sock` (`flatshare-engine-proxy.socket`) |
| Gray (second GPU node on a shared host, used in windows when no other user's work holds its GPU: the two-card rounds' second card and the serving arrangement's warm spare) | The same units as Phastform, with Gray's drop-ins (`deploy/gray/systemd/`: the CUDA compiler from the engine venv, the engine on cores 0–7 of NUMA node 0, the GPU's, and the audio servers on cores 8–15 of node 1), and `deploy/gray/private-net-host.conf` in all three: Gray's kernel refuses unprivileged user namespaces, so its install runs the servers in the host's network namespace ([below](#a-gpu-node-without-user-namespaces-gray)). `flatshare.target` is not enabled at boot | As on Phastform: no TCP listener but the engine cores' loopback ones on ephemeral ports, which the listener audit accepts there, with CUDA's abstract sockets |
| cyan (control) | `flatshare-tunnel@phastform`, `flatshare-gateway`, `flatshare-voicenet`, `flatshare-livekit`, `flatshare-voice-worker`; `flatshare-smg` for E2 arm 8b only; `flatshare-tunnel@gray`, which `install.sh` enables at boot while `gateway.toml` reaches Gray's sockets and cyan has its target (`tunnel-gray.env`), and E2 points on Gray start otherwise | The gateway's 127.0.0.1:18080, the only TCP listener in the host's network. Unix sockets in `/run/user/$UID/flatshare/` (0700): the gateway's `gateway.sock`, and the GPU node's through its tunnel, `phastform-engine.sock`, `phastform-stt.sock` and `phastform-tts.sock`. LiveKit 17880 (TCP) and 17882 (UDP), SMG 18090 and its metrics 18091 (arm 8b), inside the voice-plane namespace only; the gateway reaches SMG at `smg.sock` |

**Cores on cyan** (48 threads):

| Cores | Used by |
|---|---|
| 0–7 | The control plane (`flatshare-gateway`) |
| 8–15 | agentic-api and tools |
| 16–31 | Load generators: AIPerf on 16–23, `flatshare-bench` on 16–31, callers on 24–31 |
| 32–47 | The voice plane: LiveKit and the worker |

The `flatshare-gateway`, `flatshare-livekit` and `flatshare-voice-worker` units set their own affinity, and load generators run under `taskset`.

## Deploy

Deploy from a workstation with SSH access to the hosts. The commands name the hosts by SSH aliases (`phastform`, `cyan`, `gray`); any host name or alias that SSH resolves works, as long as its first label is the host's directory under `deploy/`, from which `deploy.sh` releases.

```sh
export FLATSHARE_SSH="ssh -F $HOME/.ssh/flatshare_config"   # your SSH command for the hosts
deploy/deploy.sh phastform                       # release HEAD's commit to Phastform: prepare, verify, switch
deploy/build-gateway.sh peacock                  # this commit's gateway, built on a Linux host with rustup
deploy/deploy.sh cyan --gateway build/flatshare-gateway-<id>
deploy/deploy.sh gray                            # the second GPU node
deploy/deploy.sh phastform --status              # its releases, current and previous
deploy/deploy.sh phastform --rollback            # back to the previous release (--to ID: another one)
```

**A release** is the commit `HEAD` names (`git archive`) and nothing else, no untracked, ignored or uncommitted file, with `DEPLOYED`, the commit's `git describe`, which every E2 point records: `deploy.sh` refuses a tree that has changes it would not carry. It uploads the release to the host and runs [`deploy/bin/flatshare-release`](../deploy/bin/flatshare-release) there, which keeps the deployment under `~/flatshare`:

| Path | What it is |
|---|---|
| `releases/ID/` | One release, ID the commit's 12-character abbreviation: its tree, read-only, with `MANIFEST.json` and `venvs/NAME`, links to its environments. The packages are compiled in it, so that nothing writes to it |
| `envs/NAME-KEY/` | A Python environment, KEY the SHA-256 of its lock file and what else decides it (a project's `pyproject.toml` and its path dependencies', uv's arguments, a vendored checkout's commit). A release whose inputs give the same KEY links it; only a changed lock builds one |
| `current`, `previous` | Links to the release the host runs, replaced in one rename, and to the one it replaced |
| `src` → `current` | The path the units and scripts name (`%h/flatshare/src/...`), and E2's `src/DEPLOYED` |
| `venvs/NAME` → `../current/venvs/NAME` | The units' `%h/flatshare/venvs/NAME/...`; `venvs/sglang`, the sglang variant's, stays a directory of its own |
| `bin/flatshare-gateway` → `../current/bin/flatshare-gateway` | On cyan, the gateway's binary, the release's; `bin/` keeps the host's own tools (`livekit-server`, `uv`) |
| `releases/history.jsonl`, `releases/running.json` | A line per switch, rollback, switch back and adoption; the release each unit was last started under |

**The manifest** (`releases/ID/MANIFEST.json`) says what the release is: the commit and its `git describe`; every file's SHA-256 and the tree's; the lock files (every `uv.lock`, `Cargo.lock` and requirements file); each environment's key, inputs, interpreter, build time, uv version and the hash of its package list; the host's own binaries that its units run (cyan's `livekit-server`), by SHA-256 and version; the gateway's binary on cyan, with its SHA-256 and its provenance (the commit, build host, toolchain and `Cargo.lock` it was built from, or the release it was carried from); the models' and tokenizer's revisions; make-room's patches and the scheduler module they build (`serving.json`'s hashes); the serving profile's effective configuration, `serving.json`; each unit's inputs, hashed; and on a GPU node whether each server runs in a network namespace of its own or in the host's (`FLATSHARE_PRIVATE_NET=host`, as on Gray, whose kernel refuses unprivileged user namespaces), with `deploy/bin/private-net-check`'s verdict and its reason.

**The steps** (`flatshare-release deploy`, which `deploy.sh` runs):
1. **Prepare.** The upload must hash to the tree `deploy.sh` staged. Each environment no release has built yet is built from its lock (the engine's with `--torch-backend cu130`, the TTS's with cu128 and the Kokoro-FastAPI checkout installed editable at its pinned commit; cyan's three from their locks, `uv sync --locked`), a build cut short is removed and built again, the manifest is written, the tree made read-only and renamed into `releases/ID`. The same commit again is the release it was.
2. **Verify**, before anything switches: every file against the manifest; each environment's imports, offline as the units run (`import vllm` at 0.32.0 and torch, the TTS's torch and Kokoro's version, the voice worker and the harness from the release); `flatshare-gateway --version` against the source's; on a GPU node the serving profile's patches and the scheduler module they build on the installed vLLM, against `serving.json`'s hash, and the Kokoro checkout at its pin; the drop-ins the host links into its units, which must exist in the release; and the models and `livekit-server`, required where a unit that runs them runs or will restart (a paused box only reports them). A check that fails switches nothing.
3. **Drain** what the switch would cut: on cyan, the voice worker in serve mode takes no new call (its drain file) and the release waits for the calls in progress to end, at most `--drain-timeout` (300 s), and switches nothing if they do not, unless `--force`; in bench mode it has no drain, and a release waits for no E2 point: one that holds the host's lock stops the release unless `--force`. On a GPU node the release waits for the engine's requests in flight to end, 60 s at most (agents keep it busy), and its restart cuts those left (the gateway answers 503 meanwhile).
4. **Switch**: `previous` to what `current` names, `current` to the release, the host's `install.sh` (its unit links, through `~/flatshare/src`), `daemon-reload`.
5. **Restart or reload** each active unit whose inputs changed: the release files it reads, its environments and binaries, compared by hash with the release before. A release of documentation (no unit's inputs include a Markdown file) or of cyan's files restarts nothing on a GPU node; a new gateway binary reloads the gateway, which hands its sockets over without a gap, and a change to its unit restarts it; `flatshare-voicenet` takes LiveKit, SMG and the voice worker with it. An inactive unit stays stopped: a paused box starts the new release when it is started.
6. **Check**: each restarted unit active and not restarting for `--settle` seconds (10); on the box, the engine's configuration against `serving.json` where it runs `make-room-serve`, printed; on cyan, the gateway's `/health` and, in serve mode, the voice worker's admission and the gateway's nodes (its `GET /nodes`, which a gateway of one upstream passes) against `serving.json`; the listener audit (`deploy/bin/audit-listeners`).
7. **On any failure after the switch** it switches back: `current` to the release before, `previous` as it was, the same units restarted on it and checked; `deploy.sh` exits 1, or 3 if switching back failed too. On success it keeps the newest 3 releases (`--keep`), current, previous and any release a running process imports from, and removes the rest and the environments none of them links.

A unit's Python processes import the release current named when the first of them started, whatever a switch does meanwhile: the environments' editable installs read the release that `FLATSHARE_RELEASE` names, which that first interpreter sets from `current` and its children inherit (the voice worker's job processes, an E2 point's tools), and pruning keeps any release a process names so. Do not release to cyan while an E2 campaign runs: a release refuses only while a point holds the lock, and one between two points would change the arm files and the harness that the next point reads. `--no-switch` prepares and verifies only, to warm a release before a window; `deploy.sh HOST --rollback` switches to `previous` by steps 2 to 7. Do not run scripts from a release's own directory: links made from there (by `variant.sh`, say) would outlive it, which is why the install scripts link through `~/flatshare/src` whichever path ran them.

**The gateway's binary.** `deploy/build-gateway.sh BUILD_HOST [OUT]` builds this commit's on a Linux host with rustup whose glibc is not newer than cyan's (peacock and cyan run Ubuntu 22.04), from `git archive HEAD` with `cargo build --release --locked -p flatshare-gateway`, into `build/flatshare-gateway-ID` and its provenance beside it (`.json`), and `deploy.sh cyan --gateway FILE` puts it in the release, refusing one built from another commit. Without `--gateway`, `deploy.sh` carries the binary of the release cyan runs when its crates (`crates/`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`) are this commit's, and refuses otherwise. `flatshare-gateway --version` names the version it was built at, which every E2 point records (`versions.flatshare_gateway`).

**Drain the voice plane before a GPU node's release.** A release of Phastform restarts its engine when the engine's inputs changed, and calls on it break. To release it without cutting calls, stop cyan's worker taking them first and let it again after: `$FLATSHARE_SSH cyan python3 flatshare/src/deploy/bin/flatshare-release drain` (serve mode; it waits for the calls in progress), then the node's `deploy.sh`, then `... flatshare-release undrain`.

**The first release on a host deployed before releases** (each host, once, paused or idle, with no E2 point or drill running; on Gray, also with no other user's process on its GPU): `--adopt` moves the old layout into a release in place before it prepares the new one: `~/flatshare/src` becomes `releases/legacy-REV` (REV its `DEPLOYED`) and `current`, the environments under `venvs/` become `envs/NAME-legacy`, cyan's `bin/flatshare-gateway` moves into the adopted release, and each old path becomes a link into `current`, each by one rename, so that a unit that runs keeps its files. The new release then builds its environments afresh and switches as above. The adopted tree need not be what its units run (the old deploy restarted none of them), so the adopted release has no unit hashes, and this first switch restarts every active unit, once: on cyan the voice plane, the tunnel and the gateway with its socket, so release it in a quiet window. `--rollback` returns to the adopted release, which has no `flatshare-release` of its own: `deploy.sh HOST --status` and `--rollback` then run the newest release's, so a second `--rollback` goes forward again. `deploy.sh HOST` does too (the release is kept, and switched to), on cyan with `--gateway FILE` again, since the adopted binary has no build to carry from.

```sh
deploy/build-gateway.sh peacock
deploy/deploy.sh phastform --adopt
deploy/deploy.sh cyan --adopt --gateway build/flatshare-gateway-<id>
deploy/deploy.sh gray --adopt
```

On cyan, `install.sh` also disables and unlinks the units of this tree that the repository no longer has (the tunnels' from before `flatshare-tunnel@.service`, say); one that still runs keeps running until the next reboot, so stop it by hand (`systemctl --user stop UNIT`).

**First time on a host:**
1. Enable lingering: `loginctl enable-linger $USER`.
2. Release to it: `deploy/deploy.sh HOST` builds its Python environments from the lock files (uv 0.11.27 or newer, in `~/.local/bin` or set by `FLATSHARE_RELEASE_UV`) and switches to the release; nothing runs yet.
3. Run its bootstrap from the release, `bash ~/flatshare/src/deploy/HOST/bootstrap.sh`:
   - Phastform: the Kokoro checkout at its pin and its weights, the FlashInfer JIT workspace and the curand header links, and the models at the revisions `engine.yaml` and `stt.yaml` pin.
   - Gray: Phastform's.
   - cyan: the LiveKit server, a check that the worker's models load offline, the LiveKit keys in `~/.config/flatshare/livekit.env` (mode 600) and the three tunnel keys (`~/.ssh/flatshare_tunnel_{engine,stt,tts}_ed25519`). Write the tunnel's SSH target to `~/.config/flatshare/tunnel-phastform.env` as `FLATSHARE_TUNNEL_TARGET=<user>@<gpu node>`.
4. Authorize the tunnel keys on each GPU node: `deploy/authorize-tunnel.sh cyan phastform` (and `gray`). Each key's entry runs one command for every session, whatever its client asks, the bridge to the node's socket of its name (`exec nc -q0 -U /run/user/$UID/flatshare/engine.sock`), under `restrict`: no forwarding of any kind, no pty, no agent, no `~/.ssh/rc`. The node needs OpenBSD's netcat (Ubuntu's `netcat-openbsd`). Re-running the script replaces the entries, and removes those of cyan's former keys: the single tunnel key that forwarded the node's ports, `~/.ssh/flatshare_tunnel_ed25519` (`lh_tunnel_ed25519` before the rename), and the sockets' keys under the former name, `lh_tunnel_engine_ed25519` and so on. They may then be deleted on cyan. For a soak's guard, `deploy/authorize-guard.sh cyan phastform` (and `gray`) authorizes one more key the same way, cyan's `~/.ssh/flatshare_guard_ed25519` (made there when it has none), whose sessions run `deploy/bin/node-report` alone: the GPU's processes and the node's units' journal lines ([Soaks](#soaks)).
5. On cyan, configure the gateway:
   - Write `~/.config/flatshare/gateway.toml` (mode 600) from `deploy/cyan/gateway.example.toml`. For each keyed tenant, make a key, give it to the client, and put only its digest in the file: `printf '%s' "$key" | sha256sum`. `cache_salt_secret_file` names the secret the tenants' cache salts are keyed by, which `deploy/cyan/install.sh` writes once (32 random bytes in hex, mode 600); the gateway refuses to start without it, or if any other user may read it. `metrics_key_file` names the key that `/metrics` asks for on the TCP listener, which `install.sh` writes once too; with a TCP listener the gateway refuses to start without it, or if any other user may read it.
   - `systemctl --user enable --now flatshare-gateway.socket flatshare-gateway`. The socket unit holds the gateway's listeners, 127.0.0.1:18080 and `gateway.sock`, and hands them to each gateway process ([below](#the-gateway)).

**A host deployed before the rename** (v1.1 and earlier, as Leaseholder): `deploy.sh` installs the `flatshare-*` units beside the old ones, and nothing reads the old names, so the host moves first, paused and with no E2 point or drill running. Both hosts moved this way on 2026-10-26:
1. Disable the `lh-*` units (and `leaseholder.target` on a GPU node), remove their links and drop-in directories from `~/.config/systemd/user`, and run `systemctl --user daemon-reload`.
2. Move `~/leaseholder` to `~/flatshare` (on cyan `~/.config/leaseholder` to `~/.config/flatshare` too), point the absolute links into the old tree at the new one (cyan's long traces), and remove `$XDG_RUNTIME_DIR/lh`.
3. On cyan, rename the variables in the env files from `LH_*` to `FLATSHARE_*`, their values unchanged; in `gateway.toml`, the paths under `/run/user/UID/lh/` and `~/.config/leaseholder/` and the units it names; and the tunnel keys from `~/.ssh/lh_tunnel_*` to `flatshare_tunnel_*`.
4. Deploy as on a new host: `deploy.sh`, the bootstrap (which rebuilds the venvs, whose scripts name the old tree), the gateway, `authorize-tunnel.sh` (which takes the entries of the keys' former names off the node too) and the units; on Phastform, `variant.sh use` the variant the box ran.

## Upgrading a component

| Component | Upgrade | Rollback |
|---|---|---|
| vLLM and the Python environments | A new lock: the release builds a new environment beside the old ones | `deploy.sh HOST --rollback`, offline and atomic |
| The gateway's binary | Carried by each release | Atomic, with the release |
| Flatshare's code and the serving profile | Each release | Atomic |
| The models | Change the revision in `engine.yaml` or `stt.yaml`, run `deploy/phastform/bootstrap.sh` on each node to fetch it (the units load offline), then release | Atomic while the old revision is still in the Hugging Face cache |
| LiveKit | Change its two pins (`livekit=` in `deploy/cyan/bootstrap.sh`, and `tools` in `deploy/bin/flatshare-release`), run `bootstrap.sh`, which replaces the binary in place, then release | Not atomic: a rollback fails its check, since the binary is not the old release's version. Run the old release's `bootstrap.sh` first |
| Kokoro-FastAPI | Change its commit where it is pinned (`flatshare-release`'s `vendor`, `deploy/phastform/bootstrap.sh` and `deploy/a100/bootstrap.sh`), run `deploy/phastform/bootstrap.sh`, which moves the shared checkout, then release | Not atomic: a release refuses a checkout at another commit. Check out the old commit first (`git -C ~/flatshare/vendor/Kokoro-FastAPI checkout COMMIT`) |

Each manual case fails closed: the release refuses to switch, rather than run a component its manifest does not name.

## State and secrets

What each restart keeps:
- **A reload** of the gateway keeps everything: its successor takes the listeners, the placements and the nodes' verdicts from the ledger.
- **A restart or a crash** of the gateway loses the placements, the verdicts and the covering state, which are memory only. Sessions are placed again by their next request.
- **A restart of LiveKit or of the voice worker** ends the calls. LiveKit's rooms are memory only.
- **A restart of the engine** loses its KV, on the GPU and in the CPU tier.

| Item | Where | If lost | Rotation |
|---|---|---|---|
| `gateway.toml` | cyan, `~/.config/flatshare/` | Written by hand: keep a copy | Edit, then `systemctl --user reload flatshare-gateway` |
| Tenants' keys | Clients hold them; `gateway.toml` holds their SHA-256 (`keys_sha256`) | Issue new ones | Add the new key's digest beside the old one, reload, move the clients, then remove the old digest and reload |
| The metrics key | cyan, `~/.config/flatshare/metrics-key` (`install.sh` makes it once) | `install.sh` makes a new one | Replace the file, then reload the gateway. Prometheus reads the file (`credentials_file`) at each scrape, so it needs no reload, and a scrape between the two gets 401 |
| The cache-salt secret | cyan, `~/.config/flatshare/cache-salt-secret` (`install.sh` makes it once) | `install.sh` makes a new one | Replace the file and reload. Every tenant's salt changes, so every prefix cache starts cold |
| LiveKit's API key and secret | cyan, `~/.config/flatshare/livekit.env` (`bootstrap.sh` makes it once) | `bootstrap.sh` makes new ones | Remove the file, run `bootstrap.sh`, then restart LiveKit and the worker in a drain window, which ends the calls |
| The tunnels' keys | cyan, `~/.ssh/flatshare_tunnel_{engine,stt,tts}_ed25519` | `bootstrap.sh` makes new ones | Remove them, run `bootstrap.sh`, run `deploy/authorize-tunnel.sh cyan NODE` for each node (it replaces the old entries), then restart `flatshare-tunnel@NODE` |
| Each tunnel's target | cyan, `~/.config/flatshare/tunnel-NODE.env` | Written by hand | Edit, then restart `flatshare-tunnel@NODE` |
| Which engine variant a node runs | The node, `~/.config/systemd/user/flatshare-engine.service.d/` | `deploy/phastform/variant.sh use make-room-serve` | |

Nothing here needs a backup but `gateway.toml` and the tunnels' targets: the scripts make the rest again, or a release restores it.

## Start, stop, status

```sh
# Phastform
systemctl --user start flatshare.target          # the three servers start at once; the box is ready when the engine is
systemctl --user stop flatshare.target
systemctl --user restart flatshare-engine        # one server; returns once /health answers
systemctl --user list-units 'flatshare-*'
journalctl --user -u flatshare-engine -f         # logs
bash ~/flatshare/src/deploy/phastform/smoke.sh   # end-to-end voice turn, GPU memory, listener audit
nsenter --target "$(systemctl --user show -p MainPID --value flatshare-engine)" --user --net --preserve-credentials \
  ss -lntup                                      # what listens inside the engine's own network namespace

# cyan
systemctl --user start flatshare-tunnel@phastform flatshare-voicenet flatshare-livekit flatshare-gateway
socket_dir=unix:$XDG_RUNTIME_DIR/flatshare           # the tunnel's sockets
bash ~/flatshare/src/deploy/phastform/smoke.sh $socket_dir/phastform-engine.sock $socket_dir/phastform-stt.sock \
  $socket_dir/phastform-tts.sock
python3 ~/flatshare/src/deploy/bin/audit-listeners   # no TCP listener of ours but the gateway's
~/flatshare/src/deploy/bin/in-voicenet ss -lntup     # what listens inside the voice-plane namespace
```

A unit counts as started only once its server answers its health endpoint (`wait-healthy` in `ExecStartPost`), the gateway once it says it is ready (`Type=notify`). Units that depend on it start only then.

## The gateway

`flatshare-gateway` serves the OpenAI routes and `/v1/events` on 127.0.0.1:18080, with an API key, and on `/run/user/$UID/flatshare/gateway.sock`, the voice plane's way in, without one. Its own `/health` and `/ready` need no key; `/metrics` and `/metrics/engine` (the engine's own, relayed) need the metrics key on the TCP listener and nothing on the socket. Its configuration reference and metrics list are in the [`flatshare-gateway` README](../crates/flatshare-gateway/README.md), including the E2 settings: `upstream_priority` (where each class's priority goes upstream: `X-Vllm-Priority`, the body's `priority`, or `X-SMG-Priority`), and the `[admission]` policies.

`flatshare-gateway.socket` holds the listening sockets and passes them to the gateway (systemd's socket activation), so they outlive any one gateway process: a connection made while no gateway accepts waits in the socket's backlog instead of being refused.

- **Reload** to take a new binary or a changed `gateway.toml`: the gateway starts its successor from the files on disk and hands it the sockets, the successor serves as soon as the old process says that it admits nothing more (at once, 2 s at most), and the old process drains, so no connection is refused. Until the old process exits, the successor counts its requests in flight and its admission point's reservations with its own, so that `max_in_flight`, the classes' and tenants' bounds and an `[admission]` policy hold over both (`flatshare_gateway_predecessor_in_flight`); a request still waiting at the old process's admission point gets 503 `draining` with `Retry-After: 1`, never having gone upstream. Copy a new binary with `install -m 755 target/release/flatshare-gateway ~/flatshare/bin/`, which replaces the file instead of writing into it: a running binary cannot be overwritten. A reload whose successor does not come up within 10 s (a broken `gateway.toml`, say) fails and changes nothing: the old process serves on, and the journal says why.
- **Restart** stops before it starts, so the connections made during its drain wait for it (realtime and interactive requests up to `drain_timeout_s`, 30 s; background ones are cut after `background_drain_s`, 5 s), and are then served.
- **A stop or restart after a reload** drains too: the unit's `ExecStop` (`deploy/bin/flatshare-gateway-stop`) sends the SIGTERM and waits for the gateway to exit, since systemd 249 would not (the successor was its predecessor's child when it said it is the main process, which the journal's "Supervising process … which is not our child" notes) and would send SIGKILL at once. The wait ends after 45 s (`--wait` on the `ExecStop` line: the drain's 30 s and a margin; raise it with `drain_timeout_s`): `flatshare-gateway-stop` then sends SIGKILL and fails, so a gateway that hangs in its drain holds up a stop or restart for 45 s, not for twice systemd's 90 s stop timeout. On a single host `deploy/bin/flatshare-svc` runs the same `ExecStop`, with `%n` expanded as systemd expands it, and sends the SIGTERM itself if the command fails.
- **A change to `[[listen]]`** takes a restart of both units, with `flatshare-gateway.socket`'s `ListenStream=` changed to match: the gateway refuses a socket that no `[[listen]]` entry names.

```sh
systemctl --user reload flatshare-gateway           # a new binary or gateway.toml, without a gap; fails if the successor does not take over
systemctl --user restart flatshare-gateway          # drains (background requests cut after 5 s), then starts; connections wait meanwhile
systemctl --user show -p MainPID flatshare-gateway  # a reload changes it: the successor is the unit's main process
```

**Moving a gateway that binds its own sockets to the socket unit** (the first deploy of `flatshare-gateway.socket`) takes one stop and start, during which connections are refused: `systemctl --user daemon-reload`, `systemctl --user stop flatshare-gateway`, `systemctl --user enable --now flatshare-gateway.socket`, `systemctl --user start flatshare-gateway`. Do not start the socket unit while the old gateway runs: its port is taken. The gateway's `[[listen]]` entries in `gateway.toml` stay as they are (`deploy/cyan/gateway.example.toml`'s).

```sh
curl -s 127.0.0.1:18080/health                    # the process is up
curl -s 127.0.0.1:18080/ready                     # 200 while the engine serves and its /health answers; else 503 and why
curl -s --unix-socket $XDG_RUNTIME_DIR/flatshare/gateway.sock localhost/metrics | grep -E 'flatshare_gateway_(request_outcomes|upstream_errors)_total'
journalctl --user -u flatshare-gateway -f         # one JSON line per request and per lifecycle event
```

E2 reads each point's request lines from this journal, so `gateway.toml` keeps `log_format = "json"`, as the example does.

`/ready` answers by the engine's state as inference finds it, not by its `/health` alone, which vLLM answers while its process lives: `warming` from the gateway's start until an inference succeeds, `serving`, `degraded` once the gateway's inference canary has failed three times in a row (`[canary] degraded_after`) with no request succeeding between, and `drained` in a drain; only `serving` is ready (`flatshare_gateway_engine_state`). The canary is a one-token completion at background priority, sent only when no request succeeded for `[canary] interval_s` (30 s) and every second while the engine warms, so a busy gateway sends none; a client's success counts as a passing canary. Requests go upstream in every state. A gateway that has just started or reloaded is warming for the moment its first canary takes, and E2's points run with the canary off ([E2 points](#e2-points)).

## Monitoring

`ops/prometheus/prometheus.example.yml` scrapes the gateway's `/metrics` and, through the gateway, the engine's (`/metrics/engine`), with the metrics key; run Prometheus as the deploy user, so that it may read the key's file. `ops/prometheus/rules.yml` holds the SLIs, the burn-rate alerts of [the two production objectives](../docs/SLO.md#the-production-objectives), the first-byte objective and the overhead objective (a page at 14.4 times the budget's rate over an hour or 6 times over six hours, a ticket at 1 times over three days) and the health alerts: the gateway unreadable, the engine not ready (the gateway answering 503), the engine degraded (its inference failing while its `/health` answers: a page) or still warming 15 minutes after the gateway's start (a ticket), the engine's metrics unrelayed, streams broken off, requests refused for capacity or ended by their deadlines (tickets), and a full KV pool with requests waiting; with `[[nodes]]` the engine's alerts hold for each node, and a node unhealthy for a minute pages (`FlatshareNodeUnhealthy`), one covering for five minutes (`FlatshareNodeCovering`) and refused calls (`FlatshareCallsRefused`) file tickets ([Two GPU nodes](#two-gpu-nodes)). The first-byte objective reads the gateway's failure-inclusive service level, 1 − good/valid by class ([the gateway's README](../crates/flatshare-gateway/README.md#accounting)): a request that fails, is refused for capacity, times out or hangs is a miss, where the first byte's histogram it read before never saw one. `ops/prometheus/rules.test.yml` is promtool's unit test of the rules (a healthy class, an engine that fails every request, half the requests timing out, another class's misses, three days at 7%, the admission coverage, a degraded and a warming engine, and the engine's metrics and KV pool per node): `make check-rules PROMTOOL=<Prometheus 3.5.0's promtool>` checks the rules and runs it. `ops/grafana/flatshare.json` is the dashboard, with the miss fraction by class, the requests offered, admitted and ended by outcome, the admission coverage, the engine's state, the canaries and the requests in flight, and a row for two GPU nodes (each node's health, sessions, placements and failover): import it with a Prometheus data source. With `[[nodes]]`, scrape each node's engine as its own job, `/metrics/engine?node=NAME` labeled with its `node`, in place of the single engine's job, which the gateway then answers 400 `node_required` (the commented jobs in `prometheus.example.yml`). The voice worker's LiveKit metrics are not scraped: its namespace has no route in. `ops/metrics/` lists the metric families of vLLM 0.32.0 and of the worker, from their sources; with the gateway's `crates/flatshare-gateway/metrics.txt` they are what `python/flatshare_bench/tests/test_ops.py` checks every expression against. `promtool check rules` and `check config` (Prometheus 3.5.0) pass on the files, the dashboard's expressions included. Each alert's `runbook_url` opens its row in [Failures](#failures).

## Engine variants

The frozen box is `deploy/phastform/engine.yaml` and the units in `deploy/phastform/systemd/`. `deploy/phastform/variant.sh use NAME|frozen [FLAG...]` makes the box run exactly one variant plus engine flags, restarting only what changes; `variant.sh use frozen` restores the frozen box. The variants, the flags the E2 arms use and how each was checked are in [`deploy/phastform/variants/README.md`](../deploy/phastform/variants/README.md):
- **Flags** go on the engine's command line through `FLATSHARE_ENGINE_FLAGS`, set by a generated drop-in (`variant-flags.conf`); vLLM takes the command line over `engine.yaml`.
- **`pr54530`**: vLLM #54530 ported to 0.32.0, generated at each start by `build.py` and loaded with `--scheduler-cls`.
- **`make-room-serve`**: the box's serving configuration, rendered from the serving profile `deploy/profiles/rtx-5060-ti-serve.toml`: `make-room` with the PRs' switches (2 preemptions a step, the budget cap with a 48-token window, no reserve) and the step cap the sweep chose (256 tokens, no long-prefill threshold, over `engine.yaml`'s) in its drop-in, under a scheduler class that writes the configuration the engine runs to `$XDG_RUNTIME_DIR/flatshare/engine-effective.json`. Each start holds it to the profile's `serving.json` (`deploy/bin/serving-check`, after the wait for `/health`) and fails on any difference. Serve with it as `variant.sh use make-room-serve` and `variant.sh measure off` ([the serving profile](../deploy/phastform/variants/README.md#the-serving-profile)).
- **`make-room`**: the change for #40004 on vLLM 0.32.0, arm 9's engine side, generated and loaded the same way: KV preemption for a waiting request of a higher priority, the budget cap that keeps lower-priority prefill out of its first tokens, and a reserve ([ARCHITECTURE.md §2](../docs/ARCHITECTURE.md#2-the-change-63350-and-63351) states the rules). Its switches are `--additional-config.make_room.*` keys: its unit sets arm 9's values, and an arm's engine flags override one. `/server_info` reports them under `additional_config`. `probe.py` measures a priority-0 request's first token behind two long priority-2 requests in a full pool (`kv`, with the reserve off), and its first and 16th tokens behind three agent prefills (`prefill`); `tail.py` measures the calls' first-token tail beside closed-loop agents.
- **`sglang`**: SGLang 0.5.22 in the engine's place, on 127.0.0.1:8000 behind the engine's socket (`flatshare-engine-proxy.socket`). Build its environment once with `bash ~/flatshare/src/deploy/phastform/variants/sglang/install.sh`. Its unit counts as started only after one sampled request, because the first one compiles FlashInfer's kernels for minutes.
- **`mps`**: the three servers as clients of one CUDA MPS daemon (`flatshare-mps.service`); the frozen box uses time-slicing ([BENCHMARKS.md](../docs/BENCHMARKS.md#voice-on-the-shared-gpu)).
- **`agents-only`**: a card for the agents alone: the STT and the TTS stay stopped (their drop-ins' `ConditionPathExists=!/`, which `variant.sh` honours), and the engine runs a KV pool of 8.4 GiB in their memory, at a budget of 0.88, with vLLM's scheduling for the card (FCFS, step cap 2,048, no per-request cap). `variant.sh use frozen`, or any other variant, starts the speech servers again ([the variant](../deploy/phastform/variants/README.md#a-card-for-the-agents-alone)).

`systemctl --user cat flatshare-engine` shows what the box runs. The generated variants (`pr54530`, `make-room`, `make-room-serve`) build their scheduler module when the engine starts, and `variant.sh` restarts only for a change of drop-ins or flags; a release restarts a running engine when its `build.py` or patches change, as they are among the engine's inputs, and a stopped one builds the new module when it starts. `variant.sh on|off NAME` adds or removes a single variant, for work outside E2. `variant.sh measure on|off` adds or removes the measurement drop-in, vLLM's development routes, which `flatshare-bench e2 run` and the drills read and a production box does without; beside `make-room-serve` it changes nothing, since the serving drop-in turns the routes off again; a campaign turns it on itself ([the routes](../deploy/phastform/variants/README.md#the-measurement-drop-in)).

## E2 points

An E2 point is one arm file (`benchmarks/e2/arms/`); `flatshare-bench e2 run ARM --out DIR` measures it on cyan, and `benchmarks/e2/campaign.sh` runs a campaign file from a workstation, switching the engine before each point ([`benchmarks/e2/README.md`](../benchmarks/e2/README.md)). What a point changes on cyan, and how to undo it:
- **The gateway.** Every point runs the gateway from `~/.config/flatshare/gateway-e2.toml` through the `e2-gateway` drop-in: `gateway.toml` with the inference canary off (`[canary] enabled = false`, so that the engine serves only the point's requests and `/ready` answers as for the recorded campaigns) and the arm's `[gateway]` table merged in.
- **The worker.** `preemptive_generation = false` links the `no-preemptive-generation` worker drop-in, and `[voice] events = false` the `no-events` one.
- **The GPU node.** A point on another node than Phastform (`flatshare-bench e2 run --node gray`, which `FLATSHARE_GPU=gray benchmarks/e2/campaign.sh` passes) starts that node's tunnel when it is not running (`flatshare-tunnel@gray`, which needs `~/.config/flatshare/tunnel-gray.env` and its keys authorized on Gray), sets the gateway's `upstream` to `gray-engine.sock` in `gateway-e2.toml`, and gives the worker the drop-in `variant-e2-node.conf` with `gray-stt.sock` and `gray-tts.sock`; `run.json` names the node.
- **SMG.** An arm with `router = "smg"` starts `flatshare-smg`, and every other arm stops it. SMG takes only http:// workers and listens on TCP only, so it runs in the voice-plane namespace between two proxies (`deploy/cyan/smg.sh`): the gateway reaches it at `$XDG_RUNTIME_DIR/flatshare/smg.sock`, and it reaches the engine at the namespace's 127.0.0.1:18000, the tunnel's socket. No other user of cyan reaches either port.
- **Undo.** `~/flatshare/venvs/bench/bin/flatshare-bench e2 reset` puts the gateway back on `gateway.toml`, preemptive generation and the events on, the worker back on Phastform's sockets, and SMG stopped; a tunnel a point started to another node stays up. A campaign runs it at its end.

Beside AIPerf's and the callers' records, each point keeps the gateway's request lines (`gateway.jsonl`, the exact first bytes), the worker's journal (`voice-worker.log`: turn lines and event counts) and the GPU's clocks and temperature (`gpu.csv`, which `campaign.sh` samples over SSH once a second while the point runs). The [`flatshare-bench` README](../python/flatshare_bench/README.md#e2-points) lists every file.

One point runs at a time: the pid of the running one is in `~/flatshare/runs/.flatshare-bench-e2.lock` on cyan, and SIGINT to it stops AIPerf and the callers and marks the point failed.

**Demo points.** The demo video needs points whose callers saved their audio. A campaign file's `save-audio` line has `campaign.sh` pass `--save-audio` to its points, as `benchmarks/e2/demo.campaign` does; by hand on cyan, with the GPU node already on the arm's engine and the measurement drop-in on (`variant.sh measure on`), it is `~/flatshare/venvs/bench/bin/flatshare-bench e2 run ARM --out ~/flatshare/runs/e2/demo/POINT --save-audio`. Each caller writes `call-<i>.wav` and `call-<i>.json` beside its turns, and `make demo-video` renders the video from `demo.campaign`'s two points ([`benchmarks/e2/README.md`](../benchmarks/e2/README.md)).

## Two GPU nodes

The gateway can front two GPU nodes (Phastform and Gray), as dedicated roles or as two mixed replicas, with deliberate failover between them rather than an implied HA claim ([`benchmarks/quality/RESOURCE-GATE.md`](../benchmarks/quality/RESOURCE-GATE.md) compares the arrangements). Each node runs the box as Phastform does (its engine, STT and TTS), and cyan reaches each through a tunnel of its own, `flatshare-tunnel@NODE`, whose sockets are `NODE-engine.sock`, `NODE-stt.sock` and `NODE-tts.sock` in `/run/user/$UID/flatshare/`. `gateway.toml` then has a `[[nodes]]` entry per node in place of `upstream`, each with its engine, roles, `max_calls`, `max_agents` (which a node with both roles must set, to a count or `"unbounded"`), and speech servers, no `[admission]` table, and optionally `[placement]` (`deploy/cyan/gateway.example.toml` has both nodes; [the gateway's README](../crates/flatshare-gateway/README.md#nodes) every key). A reload takes the change, and the successor keeps every session's node. Lowering `max_agents` or `max_calls` takes effect for new sessions; placed ones keep their nodes until they end.

```sh
curl -s --unix-socket $XDG_RUNTIME_DIR/flatshare/gateway.sock localhost/nodes | jq   # each node's verdict, components, calls and agents, and the placement
curl -s 127.0.0.1:18080/ready                                                       # 200 while each role has an available node
```

- **Health.** A node is healthy while its engine serves (its own canary, idle-only) and is ready, and its STT and TTS answer `/health`: checked every second, unhealthy after 3 failed checks in a row, healthy again after 2 passed ones. A node whose engine a request found broken is passed over at once. `flatshare_gateway_node_healthy`, `node_component_healthy` and `engine_state{node=...}` show it, and `/nodes` says which component failed.
- **Placement.** Each call is placed on a node with the realtime role and a free call slot (`max_calls`), the fewest calls first, or the first such node in `gateway.toml`'s order with `[placement] calls = "fill"`, and stays there; each agent's session on a node with the background role and a free agent slot (fewer sessions than its `max_agents`, where that is a count), the fewest agents' sessions first, and stays there for its prefix cache, until it has gone `idle_s` (300 s) without a request. An agent's session that finds every such node at its `max_agents` gets 503 `no_agent_slot`, and its next request tries again. An agent's request that names no session takes no slot: it goes only to a node that carries no call and is below its `max_agents`, or to an unbounded one, and gets 503 `no_agent_slot` when there is none. The voice worker places each call with `POST /v1/sessions` before it speaks and binds the call's STT and TTS to the node's sockets the answer names, and ends the placement with `DELETE /v1/sessions/{id}` when the call ends, or when its job does not run after all, which frees the call slot at once.
- **When a node fails** (`FlatshareNodeUnhealthy`): it takes no new session, and each of its sessions moves to the other node by its next request (`flatshare_gateway_placements_total{reason="moved"}`), its KV left behind. A call's turn that was waiting for its first content when the node failed is sent once more on the other node, within its deadlines, and the caller hears nothing of the failed attempt; a turn whose reply had begun ends with an error event, and the worker must not append a new generation to the half-said reply: the next turn goes to the other node. A call's next `POST /v1/sessions` names the new node, and the worker binds its speech servers there. The survivor must have a call slot for each call: one that does not fit gets 503 `no_call_slot`, as does a new call, which the worker's admission refuses. A moved agent's session needs a free agent slot there too, or gets 503 `no_agent_slot` until one frees. While the survivor carries calls moved from the failed node it covers (`FlatshareNodeCovering`): its agents' requests wait (`failover_background_max_in_flight`, 0) until those calls end, at their `DELETE /v1/sessions/{id}` (or `session_closed`) or `idle_s` after their last turn, even once the failed node is healthy again, or are answered 503 `queue_timeout` after their class's `queue_timeout_s`; those already running finish, and agents' sessions placed on the survivor stay there and wait.
- **Recovery.** Restart the failed node's engine or speech server (`systemctl --user restart flatshare-engine` on the node, or let `Restart=on-failure` do it). The node is healthy again after 2 passed checks; the moved sessions stay where they are, new ones go to it again, and the survivor's agents run again once the calls moved to it have ended, not at once, so that those calls never run beside its whole agent load.
- **Sizing.** For the survivor to keep every call, each node's `max_calls` must hold every call the worker admits: for two mixed replicas of one call each, `max_calls = 2` on both and two calls in all at the worker. A node that carries calls holds its agents to `max_agents`, the serving profile's envelope beside its calls: the most agents' sessions its card serves beside both calls within the voice SLO, as measured for that card. `calls = "fill"` makes the second node a warm spare that takes the calls only when the first fails: the first, with `max_calls = 2` and its envelope as `max_agents`, carries both calls and never covers for them, and the second runs agents up to its own `max_agents` (12 in the serving arrangement) while it carries no call. While the spare carries any call, moved there or placed there new while the first node was down, it covers: its agents' requests are held to `failover_background_max_in_flight` until its calls end, whether or not the first node is healthy again. A bounded node counts sessions, not requests: a session holds its agent slot until its client ends it (`DELETE /v1/sessions/{id}`, or a `session_closed` event) or it has gone `idle_s` without a request. A client that starts new sessions as its old ones end without ending them, as AIPerf's replay does, finds the ended sessions' slots taken until they idle out, its new sessions answered 503 `no_agent_slot` meanwhile; so set `idle_s` just above the agents' longest pause between requests (150 s for the replay, whose think times are capped at 120 s) and offer a few sessions under the bounds ([the two-node smokes](../benchmarks/results/2026-10-28-two-node-smoke/README.md)).
- **The drill.** `ops/drills/node-failover.sh kill|stop` places two calls and runs their turns every 3 s beside two agents' streams, kills (or stops) the engine of the first call's node, and reports the turns before and after, the moves, when the node was passed over and healthy again, and how long the survivor covered for it ([Drills](#drills)).

There is no graceful drain of one node: stopping a node's engine for maintenance is a failure that the calls ride out as above.

**Gray's windows.** Gray is shared, so its servers start for a window by hand (`systemctl --user start flatshare.target` on Gray, and `stop` after), and its target is not enabled at boot (`deploy/gray/install.sh`). cyan's tunnel to it is, while the gateway uses it: cyan's `install.sh`, which each release runs, enables `flatshare-tunnel@gray` while `gateway.toml` names Gray's sockets and cyan has its target (`tunnel-gray.env`), and says so when the target is missing. It never disables one, so when a window ends, reload the gateway without Gray's node, then `systemctl --user disable --now flatshare-tunnel@gray`.

## Drills

The failure drills run from a workstation with SSH to the hosts, on the variant the GPU node runs, with no E2 point running (they take the same lock on cyan). Each writes its directory under `~/flatshare/runs/drills` and prints its summary:
- `ops/drills/drill.sh engine-kill` opens two realtime streams (the voice plane's socket) and four background ones (the TCP port, the agents tenant's key) through the gateway, then sends SIGKILL to every process of `flatshare-engine`, as an OOM kill or a crash would end it. It records how each stream ended and when, what new requests get from the kill on, how long until one succeeds again, the engine's restart from its journal, and `/dev/shm` before and after, where the CPU tier lives. The final build's drill, on 2026-10-25: every stream got the `upstream_unavailable` error event 8 to 11 ms after the kill; the engine's main process was gone 0.14 s after it and its last process 7.6 s after it (the GPU's teardown, which systemd waits for); systemd started it RestartSec (5 s) after that; its warm start listened 92.1 s later; and the first request succeeded 106.2 s after the kill ([the drills](../docs/BENCHMARKS.md#failure-drills) set it beside W8's, before the W6 hardening).
- `ops/drills/drill.sh gateway-reload`, `gateway-restart` and `gateway-kill` do the same on cyan with `systemctl --user reload flatshare-gateway` (a deploy's), `restart flatshare-gateway`, and SIGKILL to the gateway (systemd starts it again a second later). The drill script writes the event's time to the run's `event` file in the same command as the event, and from the moment the client sees it, it probes both planes every second, each probe on a new connection, beside the streams, until they have ended and requests succeed again; every attempt is kept with when it was sent and answered. The client also samples the engine's running and waiting requests from the streams' first bytes on, each sample stamped, and the report says when none was left: a gateway that dies must not leave its requests running in the engine. A reload should show no failed probe and every voice turn whole; a restart no failed probe either, but answers that come only once its drain is done; a kill the in-flight streams broken, the engine's requests gone within a second or so, and the probes answered once the gateway is back.
- `~/flatshare/venvs/bench/bin/flatshare-bench drill cpu-tier --out FILE`, on cyan with the engine otherwise idle, stores twice the CPU tier's capacity of unique prompts and checks that the tier evicted the oldest prompt and still restores the latest.
- `ops/drills/node-failover.sh kill|stop`, with the gateway on two `[[nodes]]`, places two calls with `POST /v1/sessions` and runs their turns every 3 s (streaming, 32 tokens) beside two agents' streams, polling `/nodes` every second; after five turns of each call it sends SIGKILL to the engine of the first call's node (`kill`; systemd starts it again) or stops it until the drill's end (`stop`), goes on for 240 s, and reports the turns before and after the event, the calls' moves, the turns that failed or were cut, when the gateway passed the node over and when it was available again, and how long a survivor covered for it. A failover does what the gateway's README says when the calls move within a turn or two, only the turns in flight at the event fail, none after the first move does, and the agents wait while the survivor covers ([Two GPU nodes](#two-gpu-nodes)). On the serving arrangement, 2026-10-28 ([the record](../benchmarks/results/2026-10-28-node-failover/README.md)): both calls' next turns went to Gray 0.7 s after SIGKILL to Phastform's engine and 1.9 s after its stop, none of the 300 turns after the events failed, Gray covered to the drills' end with its agents' new requests held to their queue timeout, and the killed engine was available again 101 s after the kill.
- `ops/drills/cold-start.sh engine|box` restarts the engine alone or the whole box and times each server's start from its journal; `--cold` empties the compile and JIT caches first, as on a new host, and puts them back after, even when the start fails. A failed start still leaves its journals. The script refuses to start while an E2 point or a drill holds cyan's lock, but does not hold the lock itself: start nothing else meanwhile.

## Soaks

A soak loads the box as it serves for hours and keeps every attempt and every scrape ([EXPERIMENTS.md](../docs/EXPERIMENTS.md#the-soak-the-production-path-for-hours) says what it measures). It runs on cyan, takes the lock of E2's points and the drills (it does not start while one holds it, and none starts while it runs), and changes nothing on the box: no unit restarted, no drop-in linked, no development route asked. It refuses to start on a box that does not serve as deployed, and says what to fix.

**Before the first soak**, once:
- **The serving arrangement.** The voice worker in serve mode ([the voice plane](#the-voice-plane)): `variant-vad-turns.conf` unlinked, the `serve` drop-in linked as `variant-serve.conf`, and the worker restarted. Its audio is then the profile's, real microphones (the end-of-turn model and LiveKit's AEC warm-up), which refuses fixed endpointing. To keep E2's fixed endpointing for the synthetic callers instead, leave `vad-turns` linked beside `serve` and add a drop-in with `Environment=FLATSHARE_AUDIO=synthetic`; the soak records which audio the worker ran. The GPU node on its serving profile (`make-room-serve`), the measurement drop-in off (`variant.sh measure off`). With two nodes, `gateway.toml` with both `[[nodes]]` and `flatshare-tunnel@gray` running ([Two GPU nodes](#two-gpu-nodes)). No E2 drop-in left on cyan (`flatshare-bench e2 reset`).
- **The guard key.** cyan has no SSH to the GPU nodes but its tunnel's keys, which reach a socket each. From a workstation, `deploy/authorize-guard.sh cyan phastform` (and `cyan gray`) makes cyan's `~/.ssh/flatshare_guard_ed25519` and lets it run one command on the node, `deploy/bin/node-report`, under `restrict`: the GPU's compute processes (`gpu-guard --list`, each the box's own or another's) and the user manager's lines about the node's flatshare units since a time the session names; the soak reaches the node at its tunnel's target. A node can go unguarded with `--guard NODE=off`, which the record says.
- **The reference.** The SLO is voice alone's p95 with the same calls, in the same worker configuration, plus 250 ms: a voice-alone soak gives it, `--agents-sessions 0` for two hours, its summary's overall p95 (`flatshare-bench soak report DIR`).

**Run one** on cyan, under a transient unit, so that it outlives the SSH session and stops cleanly (SIGTERM to the soak alone, then the time its drain needs):

```sh
bench=~/flatshare/venvs/bench/bin/flatshare-bench
soak() { systemd-run --user --unit flatshare-soak --collect -p KillMode=mixed -p TimeoutStopSec=900 $bench soak run "$@"; }
soak --hours 2 --agents-sessions 0 --out ~/flatshare/runs/soak/ref-voice-alone   # the reference, first
$bench soak report ~/flatshare/runs/soak/ref-voice-alone                         # once it has ended: its p95 is P95
soak --hours 24 --slo-reference P95 --calls-per-hour 20 --turns 10 --agents-sessions 14 --agents-data weka-x32-long \
  --out ~/flatshare/runs/soak/NAME     # two nodes bounding agents at 4 + 12: a few under the bounds (Two GPU nodes, Sizing)
journalctl --user -u flatshare-soak -f      # its progress: each tool's run, each hour's line
systemctl --user stop flatshare-soak        # ends it early, its summary written
```

The nodes are the gateway's: its `[[nodes]]`, or the node its `upstream` socket names (`phastform-engine.sock`), each guarded over SSH unless `--guard` says otherwise. At the window's end no call arrives any more, the calls in progress play their turns (for `--drain-s`, 600 s, at most) and AIPerf stops. SIGINT or SIGTERM ends a soak the same way, each call with its current turn; a second one hangs the calls up. A tool that ends early starts again, after a backoff if it keeps ending (10 s, then up to 10 minutes). While a guarded GPU holds another's process, or cannot be read three minutes in a row, the soak stops its calls and AIPerf, and starts them again once every GPU has been clear for five minutes (`--guard-clear-s`): the gateway places the load, so a pause stops all of it.

**What it records**, in the soak directory: `soak.json` (the options, the versions, how the box served: the worker's settings and status, the serving profile, the gateway's configuration without key digests, the nodes and their guards; each run of the callers and of AIPerf; the pauses; how it ended), `soak.log`, `events.jsonl` (each tool's runs, the guard's episodes, failed scrapes, counters that went down, units whose state changed), `calls/run-NNN/` (`attempts.jsonl`, a line an attempt, and `turns.jsonl`, a line a turn), `agents/run-NNN/` (AIPerf's log and exports), `series.jsonl` (the kept series of every scrape), `scrapes/HOUR.gz` (every scrape whole), `units.jsonl` (the user managers' lines about the flatshare units, cyan's and the guarded GPU nodes', a failure's with the unit's own last lines), `guard.jsonl` (every check) and `summary.json` with `summary.md`, written as each hour ends. A 24-hour soak leaves about 40 MB on cyan (half of it the raw scrapes, half `series.jsonl`) beside AIPerf's per-request export, a few KB a request.

**Reading the summary** (`flatshare-bench soak report DIR`, per hour and overall): **calls** attempted, accepted, refused by reason (`capacity`: the worker was full, which is admission working; `placement`: with node binding, the gateway placed the call on no GPU node, which its `placements_refused` counts too; `engine`, `draining`, `no_agent`: a dispatch LiveKit lost) and failed; **turns** measured and failed; **replies**, their pooled p95 and the share over the SLO, which should stay within 5% ([SLO.md](../docs/SLO.md)); **pauses over 500 ms**; the gateway's **realtime SLI**, good over valid from its own counters; **background** requests offered, admitted, completed and failed, and their tokens a second; each engine's preemptions and KV use; **restarts** (the units' failures, scheduled restarts and starts, counters that went down) and the guard's pauses. An hour that differs from the rest points at `events.jsonl` and `units.jsonl` for the same hour. A GPU node's units come through its guard, named `NODE:UNIT` (`phastform:flatshare-engine.service`); an unguarded node's are not read.

**Commit it** as a compact record: `flatshare-bench soak export DIR --out benchmarks/results/DATE-soak` writes `soak.json`, `attempts.jsonl`, `turns.csv`, `series.csv` (a column a kept series), `events.jsonl`, `units.jsonl`, `guard.csv` and the summary, a few MB for 24 hours, with no raw scrape, AIPerf export, request log or credential, every path under a home directory written from `~` and the login such a path names written as `USER` wherever else it appears (the export refuses a record that still names either); `soak report` gives the same summary from it.

## Checks before heavy work on a shared host

- `nvidia-smi` and `who`. `gpu-guard` refuses to start a GPU unit while another user's process holds the GPU, or when `nvidia-smi` cannot list the GPU's processes. It cannot stop work that starts after the units; another user's processes run in their own tmux, which `tmux ls` does not show.
- While a campaign measures, `nvidia-smi --query-compute-apps=pid,used_memory --format=csv` on the GPU node lists only the box's units (their cgroups end in `flatshare-*.service`). A point measured while any other process held the GPU is measured again.
- `free -g`, and `df -h /dev/shm`: the CPU tier occupies 20 GiB there.
- Listener audit, as `python3 ~/flatshare/src/deploy/bin/audit-listeners` checks it on either host (`deploy.sh` runs it after each install):
  - on Phastform, the audit with the three sockets expected finds the servers listening on them and none of the box's units on TCP, but for the SGLang variant's engine on loopback:

    ```sh
    python3 ~/flatshare/src/deploy/bin/audit-listeners --expect $XDG_RUNTIME_DIR/flatshare/engine.sock \
      --expect $XDG_RUNTIME_DIR/flatshare/stt.sock --expect $XDG_RUNTIME_DIR/flatshare/tts.sock
    ```

    The host's `ss -Hlx` does not list those sockets: each server listens in a network namespace of its own, whose sockets the audit reads from the namespace's own table (`ls -l /run/user/$UID/flatshare/` shows the files; the `nsenter` line under [Start, stop, status](#start-stop-status) shows what listens in the engine's namespace);
  - on cyan: `ss -Hlntup` shows no LiveKit socket on the host network.

## A GPU node without user namespaces (Gray)

Gray runs Ubuntu 24.04 with `kernel.apparmor_restrict_unprivileged_userns=1`, and the deploying user has no root to lift it: `unshare --user` fails there ("write failed /proc/self/uid_map: Operation not permitted"), so `in-private-net` cannot give a GPU server a network namespace of its own, and fails the unit of one that asks for it. Gray's install handles it at every release ([HARDWARE.md](../docs/HARDWARE.md#a-gpu-node-without-user-namespaces-gray)):

- `deploy/gray/install.sh` runs `deploy/bin/private-net-check`, which tries what `in-private-net` does and prints `allowed`, `refused: REASON` (unshare's own error, and the sysctl's value) or `unknown: REASON`. Refused, it links `deploy/gray/private-net-host.conf` into `flatshare-engine`'s, `flatshare-stt`'s and `flatshare-tts`'s drop-ins as `private-net-host.conf` (replacing a hand-made one of that name), which marks them `FLATSHARE_PRIVATE_NET=host`; allowed, it removes them; unknown, it changes nothing and says so. A server takes the change at its next start.
- The servers then run in the host's network namespace and serve only their Unix sockets in `$XDG_RUNTIME_DIR/flatshare` (0700). The listener audit, with the three sockets expected, accepts there only the loopback TCP listeners of vLLM's engine cores on ephemeral ports (torch's gloo groups) and CUDA's abstract sockets, counted apart, which the host's other users can reach, and fails on anything else of theirs:

  ```sh
  python3 ~/flatshare/src/deploy/bin/audit-listeners --expect $XDG_RUNTIME_DIR/flatshare/engine.sock \
    --expect $XDG_RUNTIME_DIR/flatshare/stt.sock --expect $XDG_RUNTIME_DIR/flatshare/tts.sock
  ```

- Each release records it in its manifest (`isolation`: where each server runs, and the check's verdict with its reason), `deploy.sh gray --status` prints it, and a release whose GPU server runs or would restart while it would ask for a namespace the kernel refuses fails its checks before any switch.
- To give each server its own namespace again: `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` (root's), then any release (or `bash ~/flatshare/src/deploy/gray/install.sh`) and a restart of the servers.

## Pausing

Nothing should hold the shared GPU while idle. To pause the GPU node, run `systemctl --user stop flatshare.target flatshare-engine flatshare-stt flatshare-tts`, which returns once the units are down (stopping the target alone returns while they still stop); restart it with `systemctl --user start flatshare.target`. The target stays enabled, so a reboot brings the frozen box back. With `[[nodes]]`, a node paused while `gateway.toml` names it is unhealthy to the gateway, and pages (`FlatshareNodeUnhealthy`): reload the gateway without it first, as a window's end does ([Two GPU nodes](#two-gpu-nodes)). Gray is on a shared host: outside the serving arrangement, start it only for a booked window (`gpu-guard` refuses while another process holds the GPU) and stop it after; as the arrangement's warm spare it runs while the arrangement serves. The engine takes about 20 s to stop, releasing its pinned CPU tier.
