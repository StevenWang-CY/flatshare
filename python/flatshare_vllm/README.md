# flatshare-vllm

The change on vLLM 0.32.0, the version E2 measured: pull requests [#63350](https://github.com/vllm-project/vllm/pull/63350) and [#63351](https://github.com/vllm-project/vllm/pull/63351) (stacked on #63350), proposed to vLLM and under review; this package runs their scheduler diff on 0.32.0 as Flatshare's `make-room` variant, beside `pr54530`, vLLM [#54530](https://github.com/vllm-project/vllm/pull/54530) ported to 0.32.0 as a baseline. A variant is a scheduler module that `build.py` writes at each engine start from the installed vLLM's own scheduler, which it never modifies. The variants' systemd drop-ins are in [`deploy/phastform/variants`](../../deploy/phastform/variants/README.md).

```text
src/flatshare_vllm/build.py      writes a variant's module: its patches, applied exactly, and the stock AsyncScheduler
src/flatshare_vllm/make-room/    63350.patch and 63351.patch, the PRs' scheduler diff backported to v0.32.0;
                                 variant.patch, what only the variant has; probe.py, tail.py and knee.sh, its GPU checks
src/flatshare_vllm/pr54530/      pr54530.patch, #54530 ported to v0.32.0 by hand; probe.py
src/flatshare_vllm/serve/        flatshare_make_room_serve.py, the serving variant's scheduler class: make-room's,
                                 which writes the configuration the engine runs as it starts
scripts/make-room-patches.sh     rewrites make-room's patches from the backport's branches, in a clone of the fork
scripts/compat_upstream.py       make compat-upstream: the PRs against vLLM's main, the patches against its newest release
tests/                           the build, make-room's behavior, make-room traced against the PRs, its cost per step
```

## The build

`python src/flatshare_vllm/build.py make-room OUT_DIR` (or `pr54530`) reads the scheduler of the vLLM the interpreter finds, applies the variant's patches in order, appends the stock `AsyncScheduler`, which then extends the patched `Scheduler`, and writes `OUT_DIR/flatshare_make_room_scheduler.py`. The engine runs it with `PYTHONPATH=OUT_DIR` and `--scheduler-cls flatshare_make_room_scheduler.AsyncScheduler`. The build needs only the standard library and finds vLLM without importing it, so the engine's own Python runs it from this source tree, with no install. Every hunk must apply at its stated line, its context and removed lines as they are there: the build refuses any installed vLLM but 0.32.0, and a source the patches do not match fails it, naming the hunk. `--source-tree` builds from a v0.32.0 source checkout, which has no package metadata to check.

The serving variant, `make-room-serve` ([`deploy/phastform/variants`](../../deploy/phastform/variants/README.md#the-serving-profile)), loads `flatshare_make_room_serve.AsyncScheduler` from `src/flatshare_vllm/serve` over the module `build.py` writes for `make-room`: make-room's `AsyncScheduler`, unchanged but for its constructor, which then writes the configuration the scheduler was built with (its switches, policy, step cap, pool, the model and its revisions, the KV connector, the vLLM version, and the SHA-256 of the module it extends and of its own file) to the file `FLATSHARE_ENGINE_EFFECTIVE` names, whole. `deploy/bin/serving-check` holds that to the serving profile.

`make-room`'s patches apply in order:
- `63350.patch` and `63351.patch`: the two PRs' changes to `vllm/v1/core/sched/scheduler.py`, backported to v0.32.0 and adapted where 0.32.0 needs it, as each patch's header says under the commit: #63350 calls make-room after 0.32.0's long-prefill threshold, since 0.32.0 has no local prefill cadence; the PRs' counters of make-room's preemptions and of the budget cap's held steps and prefill tokens stay in the scheduler, since 0.32.0's `SchedulerStats` has no fields for them; and #63351's check of a waiting queue for a lower priority is the scheduler's own, since the request queues stay stock.
- `variant.patch`: what only the variant has. Its switches are keys of `--additional-config`'s `make_room` table, validated at engine start, instead of the PRs' `SchedulerConfig` fields; it adds the reserve, which requests of a positive priority value leave free, and logs the PRs' counters, with its own of the admissions the budget cap holds back, at most every 10 s ([`deploy/phastform/variants`](../../deploy/phastform/variants/README.md) has the keys).

## One source for the change

The PRs are the change's only source. A change is made on their branches, on vLLM main (`priority-make-room-kv` and `priority-prefill-budget-cap` on the fork [StevenWang-CY/vllm](https://github.com/StevenWang-CY/vllm)), and cherry-picked onto the backport: three branches of v0.32.0 that the fork publishes, `v0.32.0-priority-make-room-kv` (#63350's commits), `v0.32.0-priority-prefill-budget-cap` (#63351's on top) and `v0.32.0-leaseholder-make-room` (the variant's commit on top). `scripts/make-room-patches.sh CLONE`, in a clone of the fork with vLLM's `v0.32.0` tag fetched into it, then rewrites the three patches from them, each the `scheduler.py` diff of one branch's commits, with the commits named in its header.

`tests/test_trace.py` keeps the variant and the PRs from drifting:

- **What it compares.** It builds the variant, and a module from the PRs' two patches alone, their `SchedulerConfig` fields read from the variant's keys. Both run the same request traces on vLLM's real scheduler, and every step's scheduled tokens by request, preempted, new, cached and resumed requests and free blocks must be equal.
- **Where.** In each switch set E2 ran (with the reserve off), synchronous and asynchronous, at watermarks 0 and 0.07, over four workloads: the behavior suite's; KV pressure, where make-room preempts under the budget cap and past two victims; random ones with shared prefixes; random ones with a KV connector's asynchronous loads, "not yet" lookups and pending frees.
- **Its negative control.** One-line mutants of the PRs' module, each of which must diverge.
- **Against another module.** `TRACE_REFERENCE=<a generated module>` compares the variant with that module instead, the reserve and the counters included: before a change lands, the module it replaces against the new one. Before #63351 bounded a step's held tokens by its budget, a module counted each of the step's held chunks against the whole budget; against such a module (W5's), the variant's held tokens need only be at most the module's.

## Upkeep: the change's cost and its fit upstream

`make perf-make-room TORCH_PYTHON=<CPU torch 2.13 with vLLM 0.32.0's dependencies>` answers whether the change still costs a scheduler step what the PRs' tables say, with its switches off and in the configuration to deploy. The environment `make test-make-room-ci` builds is one, and the checked-in baseline was measured in it: from the repository's root, `make build/cpu-env/synced`, then `TORCH_PYTHON=$PWD/build/cpu-env/bin/python` (an absolute path, since the recipe runs it from `python/flatshare_vllm`).

- **What it times.** `tests/perf_schedule.py` times `Scheduler.schedule()` in the 13 steady states of the PRs' cost tables for stock vLLM's own scheduler and for make-room's module with its switches off and in the configuration to deploy (2, true, 48, 0). A process times one state: two schedulers of each configuration, and two more of off for the noise, take turns, and a configuration's cost is its cheaper scheduler's 10th-percentile step (inclusive). What else runs on the machine slows the schedulers alike, and one scheduler that runs slower than its twin all along, as their places in memory differ, does not count.
- **What it checks.** A state has two ratios, each the median over its processes of each one's own: off/stock - 1, what the change costs a step with its switches off, which the PRs measured as main's; and on/off - 1, what it costs in the configuration to deploy. On peacock, off/stock is 0.0% to 1.1% (0 to 30 µs a step). The check prints a table of each, writes `build/perf-make-room.json`, and fails a state whose ratio exceeds the one in `benchmarks/perf/make-room-schedule.json` by more than that baseline's tolerance, measured again over six more processes first. A cost common to off and on, which on/off cannot see, fails off/stock. A ratio that fell below the baseline's by more than the tolerance passes, with a note: the baseline no longer describes the code.
- **The tolerance.** 7% for the baseline measured on peacock, a shared 2.1 GHz Xeon: twice the worst difference there between two measurements of something unchanged. Those are off against off, the median over a state's processes (at most 0.5%), and the baseline's two halves, 3 rounds each: at most 2.5% in on/off and 3.0% in off/stock, both in A16.
- **What "ok" means.** That the change's cost a step grew by less than the tolerance of the step it adds to: the step with the switches on for on/off, and with them off for off/stock. Each table's "fails past" column gives that in µs for each state: a small share of the change's own cost where it costs much (the B states) and a large one where it costs little (the A states). The 10th-percentile step does not see work added to fewer than about 9 steps in 10 (each state's on/off by the median step is kept in the JSON, unchecked).
- **Its negative control** (`tests/test_perf_control.py`) runs after the check. make-room with two of #63350's optimizations undone (giving up on room before counting the decodes' growth, checking a fit against a bound first) must fail on/off at B64 and C256; make-room that looks the waiting head's prefix-cache hit up with its switches off, as it does with them on, must fail off/stock at B16 and C16; and make-room must pass in all four. On peacock they fail by 15% to 67%.
- **A busy machine.** A run whose 1-minute load went past the baseline's highest by half prints a warning beside its verdict, since a state that fails under such load may fail for it.
- **Another machine.** A ratio does not move on a machine that is uniformly faster or slower, but a different CPU weights the change's code differently: on an M5 Max, on/off came within 1.5% of peacock's in 11 of the 13 states but 3.5% and 3.6% above it in B16 and C16, and off/stock within 0.5% in all 13. So the check compares this machine's CPU, Python and torch with the baseline's before it times anything, and refuses a difference (exit 2; the script's `--any-machine` checks anyway, with a warning). On another machine, measure its own baseline first, into a file of its own rather than over the tracked one (`make perf-make-room UPDATE=1 PERF_BASELINE=build/perf-baseline.json PERF_BESIDE=<what else ran on the machine>`, two halves of 3 rounds, each round every state once), and check against that (`PERF_BASELINE=build/perf-baseline.json`); the negative control then runs against it too.
- **Exit status.** `tests/perf_schedule.py` exits 0 when every state is within the tolerance, 1 when one costs more, and 2 when it could not measure: no torch or vLLM's scheduler, a baseline missing, unreadable or measured otherwise, or a measuring process that failed or left its steady state. make exits 2 for any failed recipe, so a job that needs to tell them apart runs the script itself (`cd python/flatshare_vllm && VLLM_TARGET_DEVICE=cpu PYTHONPATH=<VLLM_SRC> <TORCH_PYTHON> tests/perf_schedule.py check <baseline>`).

`make compat-upstream [TORCH_PYTHON=<an interpreter for vLLM main's scheduler and tests>]` answers whether the PRs still fit vLLM's moving main and whether make-room fits a newer release. `scripts/compat_upstream.py` fetches vLLM's main, the PRs' heads and the release tags into a blobless clone in `~/.cache/flatshare/vllm-upstream`, says for each PR whether main holds it already (vLLM squash-merges, so a commit of main whose subject ends with the PR's number, a true merge, or a merge that would change nothing) and otherwise whether it merges into main cleanly (`git merge-tree --write-tree`, git 2.38 or newer) or which files conflict, a PR stacked on one main holds by its own changes alone (`--merge-base`, git 2.40), runs the test files each PR adds or changes on its merge on CPU when given an interpreter (each step that runs it within `--timeout` seconds, 900 by default, or its files fail), and builds make-room (`build.py make-room OUT --source-tree`) on the newest release and on a newer release candidate if there is one. It exits 1 for a conflict or a failing test, a test that fails on main too being reported as main's, and for patches that do not apply to v0.32.0; 2 when it could not check: no network, an older git, an interpreter that cannot import main's scheduler or collect its tests, said as such rather than blamed on the PRs, or a PR none of whose tests ran (every one skipped is no evidence); and 0 otherwise. Patches that do not apply to a newer release are reported with the first hunk that fails and the size of that release's change to `scheduler.py`, and exit 0: make-room is written against 0.32.0, the pinned and deployed version, on which they must apply.

## Tests

`tests/test_build.py` builds both variants from a vLLM v0.32.0 source checkout's scheduler and checks that each module is the scheduler with its patches as `git apply` applies them, then the stock `AsyncScheduler`; that a source the patches do not match, or another installed vLLM, fails the build; and how hunks are matched. It needs no GPU, torch or installed vLLM. CI runs it with `make test-vllm`, which makes a sparse checkout in `~/.cache/flatshare/vllm-v0.32.0` on first use; `VLLM_SRC` points it at another checkout, and its build tests skip without one:

```sh
VLLM_SRC=~/src/vllm-v0.32.0 uv run --extra test pytest      # in python/flatshare_vllm
```

`test_build.py` also holds the serving profile's SHA-256 of the module (`deploy/profiles/rtx-5060-ti-serve.toml`) to the one it builds, so that a change to a patch changes the profile with it.

`tests/test_serve.py` checks the serving variant's scheduler on vLLM's real v1 scheduler, on CPU, in the environment of `tests/test_make_room.py` (`make test-make-room` runs both): it schedules as make-room's `AsyncScheduler` step for step on the behavior suite's workload and the trace suite's KV pressure, writes every setting the box's `serving.json` names, and `deploy/bin/serving-check` passes a profile of its own values and fails one that differs.

`tests/test_make_room.py` checks the `make-room` variant's behavior on vLLM's real v1 scheduler, on CPU, with hand-made requests and no model, as vLLM's own `tests/v1/core` do:

- **The KV preemption** for a waiting higher-priority request under KV pressure: the request chosen, the victims and their order, shared prefixes, the per-step cap, deferred block frees, LoRA adapters, a request the waiting loop skips.
- **The budget cap:** lower-priority prefill sits out a request's first tokens from the step it fits or its KV load is done, and the first steps of a load only, and not for a request that does not fit; its window holds as many steps under asynchronous scheduling, a step in flight counted, as without.
- **The reserve**, the switches' validation, and stock behavior with the switches off.

A stand-in KV connector loads a request's KV asynchronously or delays it. `tests/test_trace.py` is the trace above. The scheduler needs torch and vLLM's dependencies, which `make test-vllm`'s environment lacks, so there these tests skip; CI's `make-room` job runs them in a CPU environment of their own (below). On the GPU node they run against the engine environment with pytest beside it, and `VLLM_TARGET_DEVICE=cpu` keeps them off the GPU:

```sh
tools=~/flatshare/cache/testtools
[[ -d $tools/pytest ]] || ~/.local/bin/uv pip install -q --target "$tools" pytest
cd ~/flatshare/src/python/flatshare_vllm
VLLM_TARGET_DEVICE=cpu PYTHONPATH=$tools ~/flatshare/venvs/engine/bin/python -m pytest -q -p no:cacheprovider tests/test_make_room.py tests/test_trace.py
```

Elsewhere, an environment with CPU torch 2.13 and vLLM 0.32.0's Python dependencies runs them on the source checkout instead, from the repository's root: `make test-make-room TORCH_PYTHON=<its python>`, and `make test-trace TORCH_PYTHON=<its python>` (`TRACE_SEEDS=100` runs the random workloads at 100 seeds, where the default is 20). Both first check that the interpreter imports pytest, torch and vLLM's scheduler, and fail if it does not, rather than let pytest skip the suites. `make test-make-room-ci` runs both as CI's `make-room` job does. It runs them in the environment that `requirements-cpu.txt` pins: Python 3.12 on Linux x86_64, CPU torch 2.13.0, and vLLM's dependencies at the engine environment's versions (`requirements-cpu.in`, compiled by the command in its header). uv builds that environment in `build/cpu-env` (`CPU_ENV`), and the target sets `FLATSHARE_NO_SKIPS=1`, under which any skipped test fails the session (`tests/conftest.py`).

The probes take their statistics from flatshare-stats (`python/flatshare_stats`), which they load from the source tree by path, so the engine's environment runs them without an install. The make-room probes' tests run in CI, with aiohttp from the test extra (the engine environment has it too), against `tests/fake_engine.py`, a stand-in for vLLM's server with a pool, a context and a fixed pace:

- `tests/test_probe.py`: `probe.py`'s requests sized from the engine's pool and context, the frozen box's sizes unchanged, and its result line as the committed outputs' check and the PR bodies' renderer parse it, on a loopback port and on a Unix socket.
- `tests/test_tail.py`: `tail.py`'s accounting of failed call turns and stopped agents, its agents and their prompts (the frozen box's unchanged, others from the pool and context), whole replies, a run's lines and an engine on its Unix socket.
- `tests/test_knee.py`: `knee.sh`, the budget cap's window sweep, against stand-ins for `variant.sh`, the engine, `journalctl` and `tail.py`.

The upkeep checks' own tests:

- `tests/test_perf_schedule.py`: the perf check's arithmetic (the ratios, the tolerance, the check, its notes and its measuring again, the tables), its exit statuses, the checked-in baseline's numbers against its rule, and, with torch and vLLM's scheduler, that each of the 13 steady states is steady for stock vLLM's scheduler as for make-room's and runs the path it is named for. `make test-vllm` runs its arithmetic, and `make test-make-room` all of it.
- `tests/test_perf_control.py`: the perf check's negative control, which times the scheduler, so only `make perf-make-room` runs it (`FLATSHARE_PERF=1`); elsewhere it skips.
- `tests/test_compat_upstream.py`: `scripts/compat_upstream.py` against a fake upstream that it builds without the developer's git config: clean, conflicting, squash-merged and stacked PRs, PR tests that pass, fail, all skip or hang, an older git, no network. `make test-vllm` runs it; its 14 tests that merge need git 2.38 or newer and skip with an older one, and two need `VLLM_SRC`.
