# ADR-0005: Loopback-only services, SSH tunnels, a private network for voice, and node-sticky KV

- **Status:** accepted, 2026-10-22
- **Deciders:** Chuyue Wang

## Context

The hosts are shared multi-user machines with public addresses and no firewall we control. Two probes on 2026-10-22 showed how easily media ports leak:
- `livekit-server --bind 127.0.0.1` still exposed its RTC ports on the public addresses;
- libwebrtc clients (the voice worker, the measurement bots) bind ICE sockets on every non-loopback interface, whatever the server's configuration.

vLLM also trusts several client-supplied inputs for scheduling and accounting: `X-Vllm-Priority`, `X-Session-ID`, `X-data-parallel-rank`, and body fields such as `priority`, `session_id` and `kv_transfer_params`.

The GPU nodes are joined by 1 GbE, slower than recomputing a prompt on the card.

## Decision

- **Loopback only** (W6 replaced the tunnels and the GPU nodes' ports with Unix sockets; [below](#unix-sockets-end-to-end-w6-2026-10-25)).
  - Every service binds 127.0.0.1.
  - Hosts reach each other only through SSH local forwards, run as `systemd --user` units that restart on failure.
  - The tunnel key is authorized on each GPU node with `restrict,port-forwarding`, `permitopen` for the listed loopback ports, a `permitlisten` that allows no listener (a privileged port), and no shell.
- **A private network for voice.** On the control host, the LiveKit server, the voice worker and the bots run inside an unprivileged network namespace (`flatshare-voicenet.service`) with no route out:
  - **Interfaces.** It holds loopback plus one dummy interface (`flatshare0`, 10.255.0.1/32, no IPv6 link-local). libwebrtc ignores loopback adapters, so with loopback alone a client gathers no ICE candidate and media never connects; the dummy gives clients an address to bind. The server still advertises only 127.0.0.1.
  - **Reaching services.** The namespace reaches the engine, the audio servers and the control plane through Unix sockets that the tunnel and the control plane expose in `$XDG_RUNTIME_DIR/flatshare/`.
- **Sanitized inputs.** The control plane removes the engine-control headers and body fields from every client request and sets its own (`flatshare_proto::headers`). Each tenant's `cache_salt` is an HMAC of the tenant's name under a secret only the control plane reads, so tenants never share prefix-cache entries.
- **Node-sticky KV.** KV never crosses the network. Sessions stick to the node that holds their KV, and failover re-prefills from the transcript.

## Consequences

- No public ports, by construction. Every smoke test and deploy check audits the listening sockets.
- The voice plane cannot reach the internet or the host network directly. Joining a call from a browser would need an explicit bridge; the demo video needs none, since it is rendered from calls the measurement callers record (`flatshare-voice bots --save-audio`).
- A tunnel adds a loopback hop on each side, sub-millisecond on this network (W6: an SSH session per connection, below). Every measured path to the engine crosses it, direct or through the control plane; the control-plane overhead in the SLO ends at the upstream write and leaves it out.
- Losing a node costs a re-prefill of its sessions. With one node the gateway handles it as an engine crash, which W8 drilled ([the drills](../BENCHMARKS.md#failure-drills), [ARCHITECTURE.md §8](../ARCHITECTURE.md#8-failure-handling)); with two, the failover drills of 2026-10-28 moved both calls to the other node within a turn, 0.7 s after a kill and 1.9 s after a stop, and no turn failed after the move ([the node drills](../../benchmarks/results/2026-10-28-node-failover/README.md)).

## Co-tenants (2026-10-24)

The hosts' other users share their loopback, which this decision does not cover. On cyan, the tunnels' TCP ports (Phastform's 18000, 18100 and 18880, and Gray's 28000-series) are reachable by any local user, and the frozen box's engine runs with `VLLM_SERVER_DEV_MODE=1`, which serves development routes such as `/collective_rpc` and `/sleep`; the harness needs `/server_info` and the cache-reset routes. The GPU nodes' own users reach the engine, STT and TTS on their loopback with no tunnel at all, and on cyan SMG's ports and the gateway's `/metrics` (no key) are reachable too. Until W5 the engine also published every cached block's token ids and session id to 127.0.0.1:5557, which nothing of ours bound, and served a replay of them on 5558, forwarded to cyan's 15558; W5 removed the endpoint, which nothing read (68eda70). KV events carry token ids, so they never go on a shared host's TCP. Closing the rest needs more than socket forwards on cyan, which `permitopen` cannot name and which the harness's TCP clients (the gateway, `flatshare-bench`, SMG) cannot use: the engine, STT and TTS on Unix sockets in a private directory on the GPU nodes, socket-to-socket forwards under a key restriction that names them, a `unix:` upstream in the gateway and Unix-socket transport in `flatshare-bench`, and development mode only in a drop-in for measurements. That is W6's production hardening. Until then every co-tenant of either host can drive the engine. The voice plane's namespace isolates its network, not its processes: they keep the deploying user's uid and reach that user's systemd bus.

## Unix sockets end to end (W6, 2026-10-25)

W6 closed what the co-tenant section lists, for the hosts' other users:
- **The GPU nodes.** The engine, STT and TTS serve on Unix sockets in `$XDG_RUNTIME_DIR/flatshare`, which their units make 0700, and on no TCP port: vLLM 0.32's `--uds` (it binds the path before the engine starts and listens once uvicorn serves, and leaves the file a killed engine had, which the units remove first) and uvicorn's `--uds` for Kokoro-FastAPI. vLLM's ZMQ sockets between its API server and engine core go in a directory of each unit's own there, which its start empties (`VLLM_RPC_BASE_PATH`): vLLM names them afresh at each start and removes none at a stop. SGLang 0.5.22 serves no socket: its variant keeps 127.0.0.1:8000, behind a proxy that serves the engine's socket, for as long as it runs.
- **The tunnels.** `permitopen` names host:port pairs only, and a key with `port-forwarding` may also ask for a listener on a socket path, which `permitlisten` does not limit (OpenSSH 8.9, `channels.c`: `remote_open_match`, "XXX add ACLs for streamlocal"). So each socket has a key of its own, authorized with `restrict` and the forced command `exec nc -q0 -U SOCKET`: OpenSSH runs a forced command for every session, whatever the client asks, and `restrict` allows no forwarding at all, local, remote or streamlocal (checked on a private sshd: the key reached its socket and nothing else, made no listener, and got no pty). `flatshare-tunnel` on cyan serves each node's sockets on cyan's own, one SSH session per connection, multiplexed over a few connections (sshd's `MaxSessions`, 10 a connection by default; a session it refuses connects on its own). A new session's first byte comes about 12 ms after it opens, where a new connection takes 165 ms, so the servers keep idle connections 60 s and their clients 55 s.
- **The harness.** The gateway takes `unix:` upstreams, with one pooled client per upstream as before; `flatshare-bench` reaches every server by an address, `http://host:port` or `unix:PATH`. AIPerf reaches the gateway, cyan's only TCP listener in its host network, with a key; `/metrics` there needs the metrics key. SMG, which takes only http:// workers and serves TCP only, runs in the voice plane's namespace between two proxies.
- **Development mode** is a drop-in for measured boxes (`deploy/phastform/measure`); a production box serves none of the development or RL routes.
- **The engine cores' own listeners** (found by the audit on Phastform, 2026-10-25). vLLM's engine cores, the engine's and the STT's, each keep six TCP listeners on 127.0.1.1 (torch's gloo groups, on ephemeral ports), and CUDA keeps abstract Unix sockets (`@cuda-uvmfd-*`), as under W5: in the host's network namespace both reach every user of the node. Each GPU server now runs in a network namespace of its own with a loopback alone ([`deploy/bin/in-private-net`](../../deploy/bin/in-private-net): an unprivileged user namespace in which the deploying user is root, `unshare --map-root-user --net`), and its socket file serves every namespace. systemd's `PrivateNetwork=` cannot do it from a user manager: systemd 249 sets up no network namespace without a user namespace, and with `PrivateUsers=` it gives each process of a unit a user namespace of its own, which cannot join the network namespace another process of the unit made, so the unit's processes land in namespaces of their own or the host's by turns (tested on Phastform). Where the kernel refuses unprivileged user namespaces (Ubuntu 24.04 restricts them), the single host's preflight says so and its drop-ins mark the servers `FLATSHARE_PRIVATE_NET=host`, which then run in the host's namespace; anywhere else a namespace that cannot be made fails the unit rather than fall back.
- **The audit.** `deploy/bin/audit-listeners` fails on any TCP listener of the box's units outside the allowed set (the gateway's port, and SGLang's on loopback), on any of their sockets outside `$XDG_RUNTIME_DIR`, and on a `flatshare` directory there that is not 0700. It reads the GPU servers' namespaces from their own tables (`/proc/PID/net`), where it accepts their listeners, which no other user reaches, and judges their file sockets as in the host's. The smoke test and `deploy.sh` run it.
- **The gateway's sockets outlive it.** `flatshare-gateway.socket` holds 127.0.0.1:18080 and `gateway.sock` (systemd's socket activation) and passes them to each gateway process, and a reload hands them from the running gateway to its successor, so that a deploy refuses no connection; before, a restart refused every one for its drain. The audit takes the user manager's hold on the gateway's port as the gateway's.

What stays open: the sockets keep other users out, not the deploying user's other processes. On the GPU nodes other work runs under the same user (`gpu-guard` tells it from the box's units), and it reaches the servers; the voice plane's processes keep that user's uid. A user of its own for the box would close it, which needs the hosts' administrators.
