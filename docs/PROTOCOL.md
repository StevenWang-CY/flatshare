# Protocol

What the gateway, `flatshare-gateway`, accepts from callers and sends to the engines. The wire types are defined once, in [`crates/flatshare-proto`](../crates/flatshare-proto); the JSON Schemas in [`crates/flatshare-proto/schema/`](../crates/flatshare-proto/schema/) are generated from them for the Python components, and [`testdata/events.jsonl`](../crates/flatshare-proto/testdata/events.jsonl) pins the event format with one example of every type. Regenerate the schemas after changing a type (a test fails until you do):

```sh
make schema    # cargo run -p flatshare-proto --bin flatshare-proto-schema
```

## Sessions

A session is one conversation, scoped to a tenant: the key by which the gateway places a request on a GPU node, follows a call's turns and names the request to the engine. The gateway resolves it from the first of these that is present:

1. `X-Session-ID`, from a trusted tenant only. The voice worker sends `voice-<room SID>`, one per LiveKit room;
2. `X-Claude-Code-Session-ID`;
3. the OpenAI `prompt_cache_key`;
4. otherwise a minted id, `m-` and 32 random hex digits.

Session ids are 1–128 characters from `[A-Za-z0-9._:-]`, so they are safe in headers. A trusted tenant's id of that form is used as it is. Any other source, and every source from an untrusted tenant, is hashed into an id scoped to the tenant, `h-` and the first 32 hex digits of SHA-256(tenant, NUL, source), so that one tenant cannot name another's session. The resolved id is returned on every proxied inference response in `X-Flatshare-Session-ID`.

## Headers

| Header | Direction | Meaning |
|---|---|---|
| `X-Session-ID` | trusted caller → gateway → engine | The session id. vLLM records it in its GPU-tier KV events, which the frozen box does not publish |
| `X-Claude-Code-Session-ID` | caller → gateway | Claude Code's own session header |
| `X-Flatshare-Class` | trusted caller → gateway | The class: `realtime`, `interactive` or `background`; from any other caller, the tenant's default class |
| `X-Flatshare-Session-ID` | gateway → caller | The session id the gateway resolved or minted |
| `X-Vllm-Priority` | gateway → engine | vLLM's priority, from the class: realtime 0, interactive 1, background 2 (lower runs first). Sent when `upstream_priority` lists `vllm-header`, the default |
| `X-SMG-Priority` | gateway → router | SMG's class: realtime `system`, interactive `interactive`, background `bulk`. Sent when `upstream_priority` lists `smg-header` (E2 arm 8b) |
| `X-Request-Id` | gateway → engine, caller | One id per request, generated by the gateway; vLLM uses it as its request id |

Every `X-Flatshare-` header ends at the gateway; none reaches the engine.

**Inputs the gateway owns.** The engines trust several inputs for scheduling, caching and accounting, so the gateway removes them from every client request and sets its own:

| Kind | Names |
|---|---|
| Headers | `X-Vllm-Priority`, `X-SMG-Priority`, `X-Session-ID` (from untrusted callers), `X-data-parallel-rank`, `X-Request-Id` |
| Body fields | vLLM's `session_id`, `priority`, `kv_transfer_params`, `ec_transfer_params`, `cache_salt`, `request_id`, `vllm_xargs`; SGLang's `rid`, `extra_key`, `session_params`, `custom_labels`, `routed_dp_rank`, `data_parallel_rank`, `disagg_prefill_dp_rank`, `bootstrap_host`, `bootstrap_port`, `bootstrap_room` |

vLLM 0.32 reads the body's `session_id` before the header, and `vllm_xargs.session_id` after it; `X-Vllm-Priority` takes precedence over the body's `priority`. When `upstream_priority` lists `body`, the gateway writes the class's engine priority into the body's `priority`, which SGLang reads (E2 arm 7b). vLLM's FCFS scheduler ignores priorities. Each tenant's `cache_salt` is the first 32 hex digits of HMAC-SHA-256 of the tenant's name, keyed by the 32 random bytes of `cache_salt_secret_file`: it depends on the tenant's name, not its key, so rotating a key keeps the tenant's cache, and without the secret the name does not give it away.

## Lifecycle events

The voice worker tells the gateway where each call is.
- **Delivery.** Trusted callers `POST` events to `/v1/events`, as one JSON object or an array of them, and get 202 `{"accepted": n, "duplicates": m}`. The voice worker posts over the gateway's Unix socket, where the voice tenant needs no key, from one background task per session, with a 1 s timeout and no retry: a late timing signal would mislead.
- **Idempotency.** Events are idempotent by `(tenant, source, event_id)` within a window (by default 100,000 ids for 10 minutes): a repeat is acknowledged and ignored.
- **Unknowns.** Unknown fields are ignored; an unknown `type` is rejected with 400, and so is the whole batch that contains it.

```json
{"event_id": "voice-RM_a1B2c3-4", "session_id": "voice-RM_a1B2c3", "at_ms": 1792650014940,
 "source": "voice-worker", "type": "interrupted", "played_ms": 1840}
```

| Field | Meaning |
|---|---|
| `event_id` | Idempotency key, unique per emitter: the voice worker sends the session id, its sender's nonce and a sequence number |
| `session_id` | The session: for a call, the requests' `X-Session-ID` (`voice-<room SID>`) |
| `at_ms` | When the emitter observed what the event reports, on its clock, in Unix epoch ms. Ordering uses the gateway's receipt time |
| `source` | `voice-worker`, `agentic-api` or `client` |
| `type` | The event type, below |

Under the lifecycle policy, the gateway keeps each realtime session's turn state from the voice events ([ARCHITECTURE.md §6](ARCHITECTURE.md#6-tested-and-not-adopted)). Every state but idle times out after `state_timeout_s` without an event, so a lost event holds a session at most that long, and a realtime request opens its session's critical window too. Under any other policy it keeps no turn state: the events are accepted and counted, and change no decision.

| `type` | Extra fields | Sent by | Under the lifecycle policy |
|---|---|---|---|
| `user_speech_started` | — | the voice worker, at VAD onset | Arms the session's KV headroom (with `trigger = "onset"`) |
| `user_turn_ended` | — | the voice worker, at the end-of-turn decision | Opens the critical window, in which background prefill is budgeted |
| `playback_started` | — | the voice worker, at the reply's first audio | Closes the critical window |
| `playback_ended` | `played_ms` | the voice worker | Back to idle |
| `interrupted` | `played_ms`, what the caller heard | the voice worker, on barge-in | The caller is speaking again |
| `session_closed` | — | the voice worker, when the caller hangs up | Forgets the session |
| `turn_started`, `turn_finished`, `tool_wait_started`, `tool_wait_ended` | `stop_reason` and token counts; `tool`, `eta_ms` | nothing: an agent framework's sink is proposed in [agentic-api#364](https://github.com/vllm-project/agentic-api/issues/364) | Accepted, no effect: E1 found that agent-side timing closes nothing ([ADR-0006](adr/0006-the-engine-change-carries-the-realtime-tier.md)) |

[`flatshare-voice`](../python/flatshare_voice/README.md#lifecycle-events-and-turn-lines) gives the LiveKit hook behind each voice event and when it fires.

## Placement

The placement of sessions on several GPU nodes (`POST /v1/sessions`), built for E2's two-node points, is parked on the `two-node` branch with them: a gateway has one upstream.

## Removed after v0.3

An engine lease hint (a key of `kv_transfer_params`), recompute-ledger rows and a header that marked synthetic requests were built for the lease and ledger design that was dropped ([ADR-0006](adr/0006-the-engine-change-carries-the-realtime-tier.md)). Nothing sent or wrote them, and they were removed after v0.3, whose tree keeps them. The gateway still strips `kv_transfer_params` and every `x-flatshare-` header from client requests.
